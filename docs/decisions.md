## D-1: C++ coding standard and memory-safety gates
Date: 2026-11-13
Phase / issue: phase 0, before issue #3
Status: accepted

Context: the rules in `CLAUDE.md` named no baseline and covered memory safety
only briefly, while phase 0 was about to fix compiler flags and linter checks.
Options: C++ Core Guidelines; MISRA C++:2023; a project-only rule list.
Decision: `docs/coding-standard.md`, based on the C++ Core Guidelines with
stricter project rules for ownership, bounds, integers, shared memory and
parsing. Sanitizer runs gate every pull request, and every parser ships with a
fuzz target.
Reason: the Core Guidelines are free to use and are checked directly by
clang-tidy; MISRA needs a paid document and commercial checkers.
Consequences: fuzz targets are written with each parser from phase 2 onward,
earlier than the phase 10 fuzzing item in the reference document, which
becomes the long-running fuzzing campaign.

## D-2: CMake 3.21 as the minimum version, presets for every build
Date: 2026-11-13
Phase / issue: 0, #2
Status: accepted

Context: the build needs named configurations (`dev`, `release`, `perf`) that give the same result on every machine and in the pipeline.
Options: CMake presets (needs CMake 3.21 or newer); wrapper scripts; documented command lines.
Decision: `CMakePresets.json` version 3, and `cmake_minimum_required(VERSION 3.21)`. Presets name no generator; CMake picks the platform default.
Reason: presets are part of CMake, so no extra tool or script is needed, and 3.21 is the oldest version that supports the preset features used.
Consequences: build directories are `build/<preset>`. A machine with an older CMake cannot build the project.

## D-3: How the compiler settings are applied, and the `perf` preset
Date: 2026-11-13
Phase / issue: 0, #2
Status: accepted

Context: section 2 of the coding standard lists the flags, but not how the build applies them, and the issue asks for a `perf` preset without defining it.
Options: flags set globally or per target; an unsupported flag skipped or fatal; `perf` as the `release` build itself or a separate build.
Decision:
- The flags are attached per target by `scada_target_defaults`. The "all builds" list is always on; the option `SCADA_HARDENING` adds the release list.
- Configuration stops if the compiler rejects a required flag or cannot provide fortify level 3. Nothing is skipped automatically.
- `release` is `Release` with hardening, with CMake's default `-O3` replaced by the `-O2` of the standard. `perf` is `RelWithDebInfo` (`-O2 -g`) with hardening and runs only tests labelled `perf`.
- `-fPIE -pie` are produced by CMake's position-independent-code support instead of being written as literal flags.
- `-U_FORTIFY_SOURCE` precedes `-D_FORTIFY_SOURCE=3`, because some toolchains predefine the macro and the redefinition would be a warning.
Reason: per-target flags keep our warning policy off third-party code added later. A fatal error is the only way a flag cannot be dropped silently. Performance must be measured with the hardening that ships, and debug information makes a regression diagnosable.
Consequences: `dev` builds have the warnings and library assertions but not the release flags. Performance figures come from the `perf` preset only. No substitute was needed: GCC 13.3 (x86-64 and ARM64 cross) and Clang 18.1 accept every flag and provide fortify level 3.

Known limit, ARM64: `-mbranch-protection=standard` is applied and our objects carry the BTI and PAC markings, but the linked executable is marked BTI-enabled only if every linked object is, including the toolchain's start files. With the cross toolchain used here they are not, so return-address signing is active and branch-target enforcement is not. This depends on the toolchain that builds the release, which is chosen with the distribution (reference 19.1); it must be checked again then.

## D-4: ARM64 is built by cross-compilation with a GNU toolchain file, or natively
Date: 2026-11-13
Phase / issue: 0, #2
Status: accepted

Context: the same source must build for ARM64 (reference 4.1). How the pipeline runs ARM64 is decided in issue P0-04.
Options: native build only; a cross toolchain file; a container image per architecture.
Decision: `cmake/toolchains/aarch64-linux-gnu.cmake` and the presets `dev-arm64` and `release-arm64` cross-compile with the compiler `aarch64-linux-gnu-g++` found on `PATH`; the prefix can be changed with `SCADA_CROSS_PREFIX`. On an ARM64 machine the normal presets build natively.

## D-5: Libraries are static; target naming
Date: 2026-11-13
Phase / issue: 0, #2
Status: accepted

Context: each service is a library plus a thin executable with the same name (`libscada-hello`, `scada-hello`), and CMake target names must be unique.
Options: static or shared libraries; target names `lib<name>` or a suffix on the executable.
Decision: libraries are static, created with `scada_add_library(<name>)` as target `lib<name>` (file `lib<name>.a`) with the alias `scada::<short name>`. Executables are created with `scada_add_executable(<name>)`.
Reason: static linking keeps each service one file to install and keeps a combined build possible; the alias gives dependants a stable name.
Consequences: libraries are not installed. Driver plugins, if the driver interface contract chooses plugins, will need a shared-library helper.

## D-6: The `check` target is a script around clang-format, clang-tidy and clang-query
Date: 2026-11-13
Phase / issue: 0, #3
Status: accepted

Context: the coding standard (section 13) names four checks in the `check` target. clang-format and clang-tidy exist; the banned-function check and the `SCADA_RT` check had to be built.
Options: for the two new checks, a text search; a clang-tidy plugin in C++; clang-query matchers on the syntax tree. For the driver, CMake script or Python.
Decision: `tools/check/scada_check.py` runs all four checks and fails on any finding. The two new checks are clang-query matchers held in that script, reported as `scada-banned` and `scada-rt`. The target needs Python 3.8 or newer and clang-format, clang-tidy and clang-query 18 or newer; the script refuses older versions.
Reason: a text search cannot tell a call from a comment, a string or a member of the same name, and cannot see which function a call is in. A plugin must be built against one LLVM version. Matchers need no build and work on the real syntax tree.
Consequences:
- The tools are needed only for `check`. A configuration without them warns, and the target fails and names what is missing.
- A source file that the build does not compile, or that does not compile with Clang, fails the check; it is never skipped.
- Different clang-format versions can lay out the same code differently. The pipeline (P0-04) must fix one version.
- LLVM (Apache-2.0 with LLVM exception) and Python (PSF licence) are tools of the build machine and are not linked or shipped. The licence report (P0-07) must list them.
- Headers are checked through the files that include them. A header that nothing includes is formatted but not analysed.

## D-7: clang-tidy configuration: errors, disabled checks, naming details
Date: 2026-11-13
Phase / issue: 0, #3
Status: accepted

Context: the coding standard (section 13) enables nine check groups and makes five of them errors, while the same section and issue #3 say that any finding fails the `check` target. `CLAUDE.md` gives the naming rules in one line.
Options: make all groups errors in `.clang-tidy`; or keep the five there and let the target fail on everything.
Decision:
- `.clang-tidy` lists the five error groups as the standard does, so editors show the rest as warnings. The `check` target runs clang-tidy with every finding as an error.
- Disabled as unworkable: `bugprone-easily-swappable-parameters` (reports every two adjacent parameters of one type, such as two streams; the only fix is a wrapper type per parameter) and `modernize-use-trailing-return-type` (asks for `auto f() -> T` on every function; the project writes the return type first).
- Naming, where `CLAUDE.md` is not specific: namespaces are `snake_case`. "Constants" are constants at namespace, class or static scope, every `constexpr` variable, enumerators and macros. A `const` local variable or parameter is a variable and is `snake_case`. Private data members end with `_`. Template type parameters are `PascalCase`.
Reason: one finding list for the gate, without changing what the standard calls an error. The naming details follow the code already merged for #2.
Consequences: a check disabled later is added to this list in the same pull request.

## D-8: How the banned list is enforced
Date: 2026-11-13
Phase / issue: 0, #3
Status: accepted

Context: some rows of the banned list (coding standard, section 12) depend on things a tool cannot see: "`strlen` on outside data", "`strtol` without full error checks", "outside reviewed helpers".
Options: leave those rows to review; or ban the functions everywhere and suppress the reviewed uses.
Decision: the check reports every use of every function and construct in the list, including `strncpy`, `strlen`, the `atoi` and `strtol` families, `memcpy`, `memmove`, `memset` and `reinterpret_cast`. A reviewed helper suppresses its own line with `// NOLINT(scada-banned): reason` (section 14). A `NOLINT` that does not name the check is not honoured. A cast to `void` to discard a value is not reported as a C-style cast.
Reason: a rule a tool cannot decide is not a gate. The suppressions make the reviewed uses visible and countable.
Consequences: the helpers of `libscada-common` and `libscada-tag` will carry the first suppressions, each listed in its pull request. Taking the address of a banned function is reported like a call.

## D-9: `SCADA_RT` and the first real-time check
Date: 2026-11-13
Phase / issue: 0, #3
Status: accepted

Context: `CLAUDE.md` requires real-time functions to be marked with `SCADA_RT` so that checks can find them. Neither the form of the annotation nor its header was specified.
Options: a comment marker; a naming convention; an attribute.
Decision:
- `SCADA_RT` is defined in `scada/common/realtime.h` of `libscada-common`. Where the compiler has the `clang::annotate` attribute it expands to `[[clang::annotate("scada_rt")]]`, otherwise to nothing. It is written first in the declaration.
- The check reports, inside a marked function or a lambda in it: `new`, `delete`, the C allocation functions, `std::make_unique`, `std::make_shared`, `std::allocate_shared`, the `printf` family and other C stream output, locking a standard mutex, constructing a standard lock object, and `pthread_mutex_lock`.
- `libscada-common` is a header-only (interface) target until P0-06 adds its first sources.
Reason: an attribute is part of the syntax tree, so the check finds the function without guessing, and a declaration in a header marks the definition too. The standard attribute syntax with a vendor namespace is not a language extension; the macro keeps GCC, which warns about unknown attributes, free of it.
Consequences:
- Only direct calls are found. A marked function that calls an unmarked function which allocates is not reported; real-time code is still reviewed against section 11.
- Project code must not use the `annotate` attribute for anything else.
- Blocking calls, system calls and C++ stream output are not on the first deny-list. They are added as the real-time code appears (phase 1, `libscada-tag`).

## D-10: GoogleTest as the unit test framework
Date: 2026-11-13
Phase / issue: 0, #4
Status: accepted

Context: the tests need one framework before any real code is written; its licence must be permissive.
Options: GoogleTest 1.17.0 (BSD-3-Clause); Catch2 3 (BSL-1.0); doctest (MIT); no framework.
Decision: GoogleTest 1.17.0, without GoogleMock. `cmake/ScadaTesting.cmake` downloads the release archive at configure time, checks its SHA-256 hash and builds it inside the build tree. `-DFETCHCONTENT_SOURCE_DIR_GOOGLETEST=<directory>` builds from an unpacked copy without network access. Its headers are treated as system headers.
Reason: it is the most widely used C++ framework, so reviewers and tools know it, and it has death tests and per-test timing that the later phases need. It must be built from source in the tree because a sanitizer needs every object in the process instrumented, and a cross build needs it for the target architecture; a copy installed on the machine gives neither.
Consequences:
- The first configuration of a build directory needs network access or the override above.
- GoogleTest is test-only and is not installed or shipped. The licence report (P0-07) must list it: GoogleTest 1.17.0, BSD-3-Clause, test-only.
- Its macro `GTEST_TEST_`, which `TEST` and `TEST_F` expand to, registers each test with `new`. The banned-function check (D-8) does not report that one expression; a `new` anywhere else in a test file is still reported. Without this, every test would need a suppression.
- After a fatal assertion such as `ASSERT_TRUE(value.has_value())`, clang-tidy still reports the access to the optional, because it cannot see through the macro. Tests write `if (!value.has_value()) { FAIL() << ...; }` instead, or compare the optional itself.

## D-11: Test kinds, labels and where tests live
Date: 2026-11-13
Phase / issue: 0, #4
Status: accepted

Context: `CLAUDE.md` names unit, integration and performance tests but not how the build tells them apart.
Options: one CTest test per test case or per executable; labels or separate build trees per kind.
Decision:
- `scada_add_test(<name> KIND unit|integration|perf ...)` creates one GoogleTest executable, registered as one CTest test with the kind as its label and a time limit of 60 s, 300 s or 600 s.
- Unit tests live in `<component>/tests/`. Integration tests live in `tests/integration/`, performance tests in `tests/perf/`, shared test code in `tests/support/`.
- `ctest --preset dev` runs unit and integration tests and prints the time per label. `ctest --preset unit` and `ctest --preset integration` run one kind. Performance tests are built everywhere but run only by `ctest --preset perf`.
- Integration tests start processes with `scada::test::ChildProcess`, which waits in `poll()` for output or exit with a timeout. The command to start is passed in an environment variable so that a cross build can put the emulator in front.
Reason: one CTest test per executable needs no test discovery at build time, which a cross build without an emulator cannot do. Performance figures from a debug build mean nothing, so no other preset runs them.
Consequences: CTest reports an executable, not a test case; the case that failed is in the test output, which the presets print on failure. `ChildProcess` uses `pidfd_open`, so the tests need Linux 5.3 or newer.

## D-12: Sanitizer and fuzz builds
Date: 2026-11-13
Phase / issue: 0, #4
Status: accepted

Context: section 13 of the coding standard requires the sanitizer runs and fuzz targets, but not how they are built.
Options: sanitizer flags per target or for the whole tree; fuzz targets built only in the fuzz build or in every build.
Decision:
- The cache variable `SCADA_SANITIZER` selects `address-undefined`, `thread` or `fuzz`; the presets `asan-ubsan`, `tsan` and `fuzz` set it. The flags apply to the whole build tree, including GoogleTest. Every finding ends the process with a failure (`-fno-sanitize-recover=all`). Configuration stops if the runtime libraries are missing, or if a sanitizer is combined with `SCADA_HARDENING`.
- `asan-ubsan` and `tsan` are debug builds with the default compiler. `fuzz` uses Clang (`clang++` on `PATH`), because libFuzzer is part of Clang, with `RelWithDebInfo`.
- `scada_add_fuzz_target(<name> ...)` creates a fuzz target with its seed corpus in `corpus/<name>/` next to it. In the `fuzz` build, the test `<name>` (label `fuzz`) runs it for `SCADA_FUZZ_SECONDS` (default 60 s) with a 10 s limit per input. In every other build the same target is linked with a driver that replays the seed corpus once, as the unit test `<name>-corpus`.
- A fuzz target lives in `<component>/fuzz/`. Inputs the fuzzer finds and the inputs that made it fail are written to the build tree, never to the source tree.
- Deliberate bugs that prove the tools work (`tests/sanitizer-fixtures/`, the toy parser in `tests/fuzz-sample/`) are test-only, are not installed, and their tests pass only if the tool reports the bug and the process fails. The fixtures are built only in the sanitizer builds, and the `check` target excludes them, as it excludes its own fixtures; the toy parser is checked, with one suppression on the planted bug.
- A fuzz target's entry point carries `// NOLINTNEXTLINE(readability-identifier-naming)`, because libFuzzer fixes the name `LLVMFuzzerTestOneInput`.
- `.clang-format` no longer wraps a comment that starts with `NOLINT`, so that a suppression keeps its check name and reason on one line (coding standard, section 14).
Reason: a sanitizer misses errors in objects that are not instrumented. Replaying the corpus in every build keeps fuzz targets compiling with GCC and on ARM64, and turns every saved input into a regression test.
Consequences: the sanitizer and fuzz builds are x86-64 presets, as section 13 requires; there are no ARM64 variants. Fuzzing needs Clang with its runtime libraries installed. A crash found by fuzzing is fixed together with adding the failing input to the seed corpus.

## D-13: The pipeline: GitHub Actions, ARM64 on a native runner
Date: 2026-11-13
Phase / issue: 0, #5
Status: accepted

Context: every pull request must build and pass its tests on x86-64 and ARM64 (reference 18.1), and the issue leaves open how ARM64 is run. D-6 requires the pipeline to fix one clang-format version.
Options, for ARM64: a GitHub-hosted ARM64 runner (`ubuntu-24.04-arm`), building and testing natively; cross-compiling on x86-64 with the `dev-arm64` presets and running the tests under user-mode emulation; running the whole job in an emulated ARM64 container.
Decision:
- `.github/workflows/pipeline.yml` runs on every pull request and every push to `main`, as six jobs that are six separate checks: `build and test (x86-64)`, `build and test (ARM64)`, `check`, `sanitizers (asan-ubsan)`, `sanitizers (tsan)` and `fuzz`. Each job runs the preset commands of `README.md` and fails when a command fails. No step is allowed to fail.
- ARM64 is built and tested natively on the hosted runner `ubuntu-24.04-arm`, with the same presets (`dev`, `release`) as x86-64. The job first checks that the machine really is `aarch64`.
- Both `build and test` jobs build `dev` and `release`, run their tests, and keep the staged install tree of `release` as an artifact for 14 days.
- The sanitizer and fuzz jobs run on x86-64 only (D-12). Fuzz targets run side by side, one per processor, each for `SCADA_FUZZ_SECONDS` (60 s). Inputs that fail are kept as an artifact.
- Tools: LLVM 18 for clang-format, clang-tidy, clang-query and the fuzzing compiler; GCC 13 and the CMake of the runner image for everything else. Each job prints the versions it used.
- The runner is set up in one place, `.github/actions/setup-build-machine`, which is the only file that names a package manager. It installs LLVM 18 and puts its tools on `PATH` under their plain names. The build scripts stay free of distribution-specific paths and tools.
- Performance tests are not run by the pipeline.
Reason: a native runner executes the tests on real ARM64 processors, so it also covers what emulation does not model faithfully (memory ordering, timing, pointer authentication), and it needs no emulator settings in the build. It is as fast as x86-64, where emulated tests run several times slower. Performance figures from shared runners vary too much between runs to gate on a target; they need a fixed machine.
Measured (run 2 of pull request #30, 2-processor ARM64 runner, 4-processor x86-64 runners): `build and test (ARM64)` 83 s, `build and test (x86-64)` 85 s, both sanitizer jobs about 60 s each, `check` about 2 min. The whole pipeline took 2 min 48 s from start to last job, with the jobs in parallel.
Consequences:
- The cross presets `dev-arm64` and `release-arm64` (D-4) stay for developers; the pipeline does not use them, so nothing checks them automatically.
- The checks gate a merge only when they are marked as required in the protection rule of `main`, which is a repository setting and not a file. Until then the rule in `CLAUDE.md` ("do not merge a pull request whose checks are failing") is the gate.
- The fuzz sample stops within 1 s because its planted bug is found at once. With real targets the fuzz job takes 60 s for every group of as many targets as the runner has processors.
- The hosted runner images change over time. A change of the GCC or CMake version shows in the "Tool versions" step; LLVM stays at 18 until this decision is changed.
- Where and how the performance tests of section 15 of the reference document run is still open. It must be decided before phase 1 is accepted, because phase 1 has the first real targets.
- GitHub's actions `actions/checkout` and `actions/upload-artifact` (both MIT) are tools of the pipeline and are not linked or shipped. The licence report (P0-07) must list them. They are referenced by major version, not by commit hash.

## D-14: `Status` carries a code and a fixed message; `Result<T>` is our own type
Date: 2026-11-13
Phase / issue: 0, #7
Status: accepted

Context: errors are returned as values (`Status`, `Result<T>`), also by the real-time functions of the tag library, which must not allocate. The documents name the two types but not their content.
Options: a code with an owned `std::string` message; a code with a message that must be a string literal; a code only. For `Result<T>`: `std::expected` (C++23, not available in C++20); a third-party type; our own.
Decision:
- `Status` is a `StatusCode` (14 values, `status.h`) plus a `StaticString`, a view that can only be built from a string literal at compile time. It owns nothing and is trivially copyable. Details that vary at run time go into the log record written where the error is handled.
- `Result<T>` is our own class holding a value or an error `Status`. Calling `value()` on an error, or building a `Result` from an OK status, ends the process through `panic()`; the check stays on in release builds (coding standard, section 7).
- The common library uses the namespace `scada`, not `scada::common`, because these names appear in every interface.
Reason: a literal message makes `Status` usable in real-time code and removes any dangling-view risk, at no cost to callers that only branch on the code. Our own `Result<T>` needs no dependency and no language level beyond C++20.
Consequences: a `Status` cannot carry a file name or a number; callers log them. `Result<T>` can be replaced by `std::expected` if the language level is raised.

## D-15: Logging through a bounded queue, to the journal's native socket
Date: 2026-11-13
Phase / issue: 0, #7
Status: accepted

Context: services log to the systemd journal in a structured format with bounded size (reference 14.6), with a stderr fallback, and logging must not block the caller for more than a bounded time (issue #7). How records reach the journal, and what happens when it stalls, was open.
Options: link `libsystemd` and call `sd_journal_send`; write the journal's native datagram protocol ourselves; print to stderr with a priority prefix only. For a stalled sink: block the caller; drop the oldest queued record; drop the new record.
Decision:
- `Logger::log` copies the record into a pre-allocated queue (default 256 records) under a mutex that is never held during sink I/O, and a worker thread per `Logger` delivers it. When the queue is full the new record is dropped and counted, and one `WARNING` record with the field `DROPPED` reports the loss once the sink recovers.
- A record is limited to a 384-byte message and 8 fields with 32-byte keys and 96-byte values; longer text is cut. Field keys follow the journal's key rule.
- The journal sink speaks the native protocol on `/run/systemd/journal/socket` with a non-blocking datagram socket. No library is linked.
- The journal is used only when `JOURNAL_STREAM` shows that the service manager connected stderr to it; otherwise, and whenever a journal send fails, the record is written to stderr as one escaped text line.
- The record's creation time is sent as the field `SCADA_TIME_NS`, because the journal stamps the later delivery time.
Reason: the native protocol is documented as stable by systemd and needs about 50 lines, while `libsystemd` would be a new dependency to record and cross-compile. Dropping the new record keeps the records that led up to a stall, which are the ones needed to diagnose it, and needs no reordering.
Consequences: records can be lost under overload, and the loss is visible in the log. The size limits keep every record inside one datagram, so the protocol's file-descriptor passing for large messages is not needed. The socket path is fixed by systemd, not by a distribution. The stderr sink bounds its wait with `poll` (100 ms) before a blocking write; another writer that fills the same pipe in between can still delay the worker thread, never a caller. Real-time code must not log (CLAUDE.md); it passes data to a non-real-time thread instead.

## D-16: The staged tree is an image of the root filesystem
Date: 2026-11-13
Phase / issue: 0, #6
Status: accepted

Context: reference 4.4 fixes absolute paths in `/usr`, `/etc` and `/var`, and `cmake --install build/<preset> --prefix stage` must produce them "under a prefix". A CMake prefix of `/usr` cannot hold `/etc` and `/var`.
Options: the install prefix is the staging root, with destinations `usr/bin`, `etc/scada` and so on; the prefix is `/usr` and staging uses `DESTDIR`; GNU install directory variables.
Decision:
- The install prefix is the staging root. `cmake/ScadaInstall.cmake` holds the destinations, relative to the root. Paths used at runtime, such as `ExecStart=` in a unit, are these destinations with a leading `/` and do not depend on the prefix.
- systemd units go to `usr/lib/systemd/system` and user definitions to `usr/lib/sysusers.d`, which are systemd's own default locations. Both are cache variables (`SCADA_INSTALL_SYSTEMD_UNITDIR`, `SCADA_INSTALL_SYSUSERSDIR`).
- The directories `etc/scada`, `usr/lib/scada`, `usr/share/scada/web` and the four under `var/lib/scada` are installed empty and owned by root. Each is handed to its service's user by the issue that adds that service. `/run/scada` and `/dev/shm/scada` are not in the tree, because they are on memory-backed filesystems; the owning services create them at runtime.
- Service users are declared with `sysusers.d` files, one per service plus one for the `scada` group.
Reason: one command with one prefix gives the whole layout, and the tree can be copied to `/` or wrapped by any package format. `sysusers.d` is part of systemd, which the design already requires, so no distribution's user tool is needed.
Consequences: the build cannot be installed to a prefix such as `/usr/local`. A distribution that builds systemd with other directories sets the two cache variables. Ownership and modes of the data directories, and the permissions of `/dev/shm/scada`, are still to be set, by the service issues and the tag database contract.

## D-17: The systemd notification protocol is implemented in `libscada-service`
Date: 2026-11-13
Phase / issue: 0, #6
Status: accepted

Context: a `Type=notify` service must send `READY=1` and `WATCHDOG=1` to the socket in `NOTIFY_SOCKET`. No dependency list or licence report exists yet (issue P0-07).
Options: link `libsystemd` (`sd_notify`); implement the documented datagram protocol; start services through a wrapper that notifies for them.
Decision:
- A new library, `libscada-service`, implements the client side of the protocol with plain sockets. It also holds `NotifyListener`, the service manager's side, which tests use in place of systemd.
- Values of `NOTIFY_SOCKET`, `WATCHDOG_USEC` and `WATCHDOG_PID` are validated as untrusted input. A service refuses to start on an invalid value instead of running without notification.
- The library uses `Fd`, `Status` and `Result<T>` of `libscada-common`. A send returns OK when there is no service manager, because nothing had to be done; `Notifier::enabled()` tells the two cases apart.
- `bind()` needs a `sockaddr*` for a `sockaddr_un`. The conversion goes through `void*` in one function, `bind_unix`, used only by `NotifyListener`. Sending uses `sendmsg()`, which takes the address as `void*` and needs no conversion.

## D-24: Tag database contract, second review: owners are threads, commands at most once, and the other outcomes
Date: 2026-11-13
Phase / issue: 1, #9
Status: accepted

Context: draft 0.2 of the tag database contract was reviewed independently from three sides (SCADA practice, C++ and lock-free correctness, Linux). All three found it fit for phase 1 only after changes. Six points needed a decision; the rest were corrections.
Options:
- Several writing threads in one process (control tasks, driver channels) against single-writer rings and queues: one ring and queue set per writing thread; all publication through one thread; a multi-producer design.
- Command queue delivery: at least once with duplicate suppression in the driver; at most once.
- Automatic control writes and "no audit, no action": exempt source AUTO; require the record for every source; leave it to phase 5.
- An owner shrinking its region file kills mapped readers: accept; hand out sealed memory from `scada-tagd`.
- Wake-up: futex with `futex_waitv` and an in-process bridge to a file descriptor; eventfd passed by `scada-tagd`.
- Scope: everything in the pull request of #9; blockers only.
Decision (by the product owner):

- Command queues deliver at most once: the driver acknowledges before executing, and on attach drains pending requests with status `ABORTED`. A request lives at most 60 seconds.

- All review findings are fixed in the pull request of #9 (contract 0.3; its section 18 lists them).
Reason: one writer per ring keeps every path lock-free and the real-time rule intact. A command that may run twice or late is worse than one that is reported as aborted (reference 14.4). Every change to the plant leaves a record, whatever its origin (reference 3.3).
Consequences: the tag-set definition must name the writing threads. A restart of the journal or audit consumer stops automatic control until it is back; the event volume of automatic writes has to be sized when the journal is designed (phases 5 and 7). A driver restart aborts commands in flight, and the operator repeats them. The base directory must be created by the platform at boot, which phase 0 packaging (#6) has to provide. Corrections that needed no decision, among them the memory fences for ARM64 and `SCADA_E_BUSY` in place of a false `OWNER_DOWN`, are listed in the contract's change log.

## D-26: Tag-set definition, its temporary file, `config_hash` and the header builder
Date: 2026-11-14
Phase / issue: 1, #11
Status: accepted

Context: issue #11 needs a tag-set definition, a temporary file format for it, `config_hash` and the image of the `header` region. The contract (sections 2, 5 and 14) fixes the layout and the limits but not how indexes are assigned, what exactly is hashed, the content of the padding and of the name pool, or the file format. The reference document expects a JSON parser and a hash from third-party projects but leaves the choice open.
Options, file format parser: a third-party JSON library; a small parser for the subset the file needs. Options, hash: a third-party cryptography library; SHA-256 written here. Options, order independence: hash and build in the order given and require a sorted file; sort inside the library. Options, user of a process: user name resolved when the header is built; numeric uid in the definition.
Decision:
- `scada::tag::TagSet` (`scada/tag/tag_set.h`) is the one interface between configuration and the data plane. `parse_tag_set_json` (`scada/tag/tag_set_json.h`) is the only code that knows the temporary file; phase 2 replaces it.
- The file is read by a parser written here for a subset of JSON: objects, lists, strings of printable ASCII without escape sequences (at most 127 bytes), whole numbers from 0 to 4,294,967,295, `true` and `false`. Unknown, repeated and missing keys are errors. No dependency is added.
- SHA-256 is implemented in `libs/scada-tag/src/sha256.cpp` and checked against the vectors of the standard. It identifies a tag set; it protects no secret.
- The library sorts: processes, owners and queues by name, their position being the process index, owner index and queue id; the slots of an owner are its tags by name. `config_hash` is the SHA-256 of the canonical encoding written in `libs/scada-tag/README.md`, which starts with a name and a version of the encoding. Generation and creation time are not hashed.
- A process is given with its numeric uid. An owner entry gets the uid of its process.
- A queue's kind is the prefix of its name (`events.`, `cmd.`, `result.`), and its record size follows from the kind. The producer and consumer are process names. The rest of the name is not checked against them (superseded for `cmd` and `result` queues by D-52).
- Layout details the contract leaves open: each slot table is padded with zero bytes to a multiple of 8 bytes; an owner without tags has an empty slot table; the name pool holds the names in directory order without terminators, and `name_pool_size` is the number of name bytes; the file ends at the next multiple of 8 bytes; in the `RegionHeader` of `header`, `owner_index` is 0 and `queue_id` is 0xFFFF. The builder leaves `ready` 0 and `state` BUILDING for `scada-tagd` to set.
- Rules added to those the contract states: `retain_now` needs `retain`; a string tag cannot be `writable_by_command` (contract 9.4: strings cannot be commanded); a queue capacity is a power of two up to 2,147,483,648, default 1,024; uid 4,294,967,295 is refused; heartbeat times are at least 1 ms. A change ring capacity that is omitted is 65,536 and is not raised automatically: an owner with more than 32,768 tags must state it.
- An error is a `Status` with a fixed message plus a `std::string detail` filled by the function, because `Status` cannot carry text made at run time (D-14). A name from outside is repeated in the detail only after it passed the name grammar.
- The time target of the issue (50,000 tags in under 1 second) is a performance test, `scada-tag-header-perf-test`, run by `ctest --preset perf`.
Reason: the file is temporary, so a dependency chosen for it would be chosen for the wrong reasons; phase 2 picks the configuration parsers with the JSON Schema work. A parser for this subset and SHA-256 are each a few hundred lines with published test vectors or a fuzz target. Sorting inside the library makes "same tag set, same hash, same handles" hold for every producer of a `TagSet`, not only for a well-behaved file. A numeric uid keeps the builder free of system calls and its result reproducible in tests.
Consequences: handles and queue ids depend on names only, so they are stable across a restart of `scada-tagd` with the same tag set, and change for tags that sort after an added or removed tag. `scada-tagd` (issue #12) calls `config_hash`, then `build_header`, writes the bytes and sets `ready` and `state`. The layout details above, the canonical encoding and the added rules must be written into the contract before it becomes 1.0 (issue P1-13); until then they are stated here and in the library's `README.md`. The numeric uid in the file is replaced by a user name when the real configuration arrives in phase 2. If a third-party cryptography library is added later for signing, `sha256.cpp` is replaced by it.
Review: a committee of three reviewers (C++, SCADA architecture, Linux systems) examined each point of this decision on 2026-11-14 and confirmed all of them. Their notes that later work must take up:
- Contract text for 1.0 (P1-13): the items above; "sorted by name" means byte-wise; an offset may equal the file size when the part it points to is empty; `DirectoryEntry.name_offset` is a byte offset into the pool, not a multiple of 8; a real limit for queue capacity; when the encoding version of `config_hash` changes; name order is the builder's rule for layout version 1, not a promise to consumers.
- `scada-tagd` (#12): the tag set must hold the process of `scada-tagd` itself; the library needs public functions to publish a header and to set `ready`, `state` and `down`, because the layout is private; reuse of a generation needs `ready` and RUNNING as well as an equal hash; the sum of all region sizes is checked before a generation is published; removal of stale temporary files matches the exact name.
- Attach (#13): accept an offset equal to the file size for an empty part.
- Tag read and write (P1-06): which string slot a STRING tag gets. Proposed: its rank among the owner's STRING tags in name order.
- Retained values (P1-09): a tag that moves to another owner, or whose owner is renamed when its process gains a second writing thread, must find its retained value.
- Phase 2 configuration: refuse uid 0 and two processes with one uid outside tests; apply the real-time heartbeat default (500 ms), which today only the temporary file parser applies; tell the user that any change of a hashed setting restarts the data plane.

## D-27: `scada-tagd`: where its logic lives, how it starts a generation and how it judges liveness
Date: 2026-11-14
Phase / issue: 1, #12
Status: accepted

Context: issue #12 adds `scada-tagd`: it creates or reuses the generation, owns `header` and `proc.tagd`, and sets and clears the `down` flag. The contract (sections 3, 10 and 11.1) fixes the files, the permissions and the liveness rules. It leaves open where the code lives while the layout is private to `libscada-tag` (D-25), what exactly "reuse" and "live process" test, how two instances are kept apart, and several details of the sweep and of the loop. The issue names "conformance tests 4 (owner-down part) and 11", which are numbers of contract 0.1.
Options, location: `scada-tagd` includes the private headers of `libscada-tag`; a public class in `libscada-tag` for the side of `scada-tagd`. Options, reuse: equal `config_hash` and layout version; also `ready` and RUNNING; also a header equal byte for byte to the one the tag set builds. Options, live process of an old generation: a fresh heartbeat in a `proc` region; a held lock on a `proc` region. Options, second instance: rely on the lock on `proc.tagd`; a lock on the base directory.
Decision:
- `scada::tag::GenerationHost` (`scada/tag/generation_host.h`) is the side of `scada-tagd` and holds everything that touches the layout or the database files. `libscada-tagd` holds the service: command line, tag-set file, log, service manager and the loop. Private to `libscada-tag`: `shared_memory.h` (the reviewed helpers that place structures on mapped memory, with the only `reinterpret_cast`), `region_file` (creation and the checks of contract 3.1 and 3.2) and `proc_region` (own region and probe). `MappedRegion` is added to `libscada-common`.
- The tag set must hold a process named `tagd` whose uid is the effective user id `scada-tagd` runs as. That user id is "the uid of the user `scada-tagd`" for the checks of contract 3.1; no user name is looked up.
- `scada-tagd` reads `/etc/scada/tag-set.json`; `--tag-set` and `--base-dir` replace the file and the base directory.
- `scada-tagd` holds an exclusive lock (`flock`) on the base directory for its whole life, besides the lock on `proc.tagd`. A second instance fails before it reads or changes anything.
- A generation is reused only if its directory has the owner and mode of the contract, its `header` passes every check of contract 3.1, is `ready` and RUNNING, has the same `config_hash`, and equals byte for byte the header this library builds for the tag set, apart from `ready`, `state`, `created_time_ns` and the `down` flags.
- "No live process" in contract 11.1, step 3, means: no `proc.*` file in the directory is locked. The lock is the one a process holds for its whole life (contract 10), so the test needs no header of the old generation.
- A new generation gets the highest number found in the base directory plus 1, also when that directory is then removed.
- Before a generation is created, the sum of the sizes of all its regions is compared with the free space of the file system of the base directory. If it does not fit, the start fails and nothing is created.
- After `current` moved, the state of the generation it pointed to is set to RETIRING (contract 11.3, step 1). Its removal while `scada-tagd` runs comes with issue P1-09; until then it is removed by the next start that builds a generation, once no process is attached.
- A region gets its real name with `renameat2` and `RENAME_NOREPLACE`, so that a file that is already there is never replaced.
- The sweep of contract 3.1 leaves a file `.tmp.<region>.<digits>` of a listed region, owned by the user of that region: it is a region being created (contract 3.2). An entry that cannot be removed is reported once. An entry under a listed name with the right owner is left, whatever its type.
- If `current` exists and is not a symbolic link, `scada-tagd` does not start. A link with another target than a generation name is replaced.
- Liveness (contract 10.1): the rules are tested in the order region, state, heartbeat, and the first that holds is the reason. A heartbeat exactly as old as the timeout is not yet down. A heartbeat newer than the time of the check is fresh. `scada-tagd` never sets its own `down` flag. Changes are logged as `process down` (WARNING) and `process up` (NOTICE); the first check of a new generation logs at INFO, because no process has attached yet.
- The loop runs every `heartbeat_check_ms`, or more often if a third of the heartbeat timeout of `tagd` or a quarter of the watchdog interval is shorter. Each round writes the heartbeat and checks liveness; the watchdog is fed from the same loop, four times in its interval.
- Open point of contract section 16, heartbeat timeout defaults: 3,000 ms and 500 ms are kept. Conformance test 5 passes with them for the part of `scada-tagd`; test 26 confirms them in issue P1-12.
- The issue's tests 4 and 11 are tests 5 and 20 of contract 0.3. This issue covers the part of `scada-tagd` in tests 5, 6, 9, 10, 11 and 20; the part of the reading library follows with attach and read (issues #13 and P1-06).
- `/dev/shm/scada` is created at boot from `usr/lib/tmpfiles.d/scada-tagd.conf` (`d /dev/shm/scada 2750 scada-tagd scada -`), installed with the service.
Reason: a public class keeps "no other code may depend on the binary layout" a build error also for `scada-tagd`. An equal hash does not prove that the header is intact or was built by the same version of the builder; a byte comparison does, and costs one pass over the header at start. A lock is released by the kernel when its process dies, so it cannot be stale as a heartbeat of unknown timeout can. The lock on the base directory closes the time between two instances reading `current` and attaching `proc.tagd`. Without the exception for temporary files, the sweep would remove a region every 250 ms while its process is still filling it.
Consequences:
- Contract text for 1.0 (issue P1-13): the lock on the base directory; the reuse test; "live process" as a held lock; the numbering of generations; the exception for temporary files in the sweep; `renameat2` without replacement; that `scada-tagd` takes its own user id; the order of the liveness rules and the two limits of the heartbeat age.
- Attach (issue #13) builds on `region_file` and `proc_region`. Until then the integration tests use the helper `scada-tag-test-peer`, which attaches a `proc` region through the same code.
- The free-space check counts an old generation that is still there as used space, so a change to a much larger tag set can be refused until the old generation is gone.
- Conformance test 11, second part, is shown with a limit on the file size and with the free-space check. A file system that is really full needs the right to mount one and is left to the conformance suite (issue P1-12).

## D-28: Attach: the C interface so far, the order of its steps, own regions, and regions of other processes
Date: 2026-11-14
Phase / issue: 1, #13
Status: accepted

Context: issue #13 adds `scada_tag_attach`, `scada_tag_detach`, `scada_tag_heartbeat` and `scada_tag_status`: a process joins the current generation, creates or reuses and repairs its own regions, and maps the regions of other processes read-only. The contract (sections 3, 6.3, 11.2 and 13) fixes the checks, the repair and the function names. It leaves open the content of `scada_status`, how return codes map to what attach can meet, several details of the regions, and how the read-only mappings behave while their files change. The issue names "conformance tests 5, 7 and 8", which are numbers of contract 0.1.
Options, where attach lives: logic in the C functions; a private C++ class with the C functions as a thin layer. Options, lock: taken after the own regions, as contract 11.2 lists it; taken first. Options, header of a client: trusted because `scada-tagd` wrote it; validated in full before use. Options, a read-only mapping whose file was replaced: unmapped at once; kept until detach. Options, `errno` with `SCADA_E_IO`: left as the last system call set it; recorded where the error is reported.
Decision:
- `scada/tag/scada_tag.h` is the C interface, usable from C and C++. It holds the 15 return codes of contract 13.3 and the five functions of this issue; the later issues add theirs. The logic is the private class `Attachment` (`src/attachment.h`); the C functions check pointers, convert `Status` to a return code and let no exception out (a failed allocation is `SCADA_E_IO` with `ENOMEM`). A public C++ wrapper is added when the first C++ service needs one.
- `scada_status` is 32 bytes: `generation`, `generation_state` (1 to 3, or 0 for a value that is no state), `process_index`, `tagd_down`, `regions_created`, `regions_reused`, `records_repaired`, and two reserved fields that are 0. `scada_tag_status` fills it and returns `SCADA_E_RETIRING` if the generation is retiring, otherwise `SCADA_E_TAGD_DOWN` if `scada-tagd` is down by the first three rules of contract 10.1, otherwise `SCADA_OK`.
- `scada_tag_heartbeat` returns `SCADA_E_RETIRING` when the generation is retiring (contract 11.3: checked on every heartbeat); the heartbeat is written all the same.
- Return codes of attach: `SCADA_E_NOT_FOUND` only for a process that is not in the process table. `SCADA_E_LAYOUT` for another magic or layout version, and also for a header or a `current` that is not valid. `SCADA_E_IO` with `ENOENT` for a missing base directory, `current` or header; with `ENOSPC` when the file system has no room; with `EAGAIN` for a generation that is BUILDING. `SCADA_E_INVALID` for a NULL argument, a name that is no process name, or a `tagd_uid` that is neither -1 nor a uid.
- `errno` for `SCADA_E_IO` is the error number the library recorded where it reported the failing call (`errno_text` in `region_file`), kept per thread, because a `Status` cannot carry it (D-14) and clean-up calls after the failure change `errno`.
- The lock on `proc.<process>` is taken before the other own regions are looked at, not after as contract 11.2 lists it. A second process of the same name then fails before it can remove or repair a region the first one is using.
- The generation directory is checked like the base directory: owned by the uid of `scada-tagd`, mode `3770`.
- The header is validated before use (coding standard, section 9): everything listed in `read_header` (`src/header_view.h`). The process, owner and queue tables are copied out after validation; the tag directory and the slot tables are checked entry by entry when they are used. A table offset may equal the file size when the table is empty (D-26). The file is at most 256 MiB; a header of the limits of contract section 14 takes about 156 MiB.
- Own regions, in addition to the checks of contract 3.1: a reused `tags` region must have the type of the tag directory in every record, a reused ring the capacity of the owner table, a reused queue the capacity and record size of the queue table. Otherwise it is removed and created again, like a region of the wrong size.
- The `RegionHeader.owner_index` of a queue region is the process index of its producer. The value of a STRING record is its string slot, the rank of the tag among the owner's STRING tags in slot order, written when the region is created (proposed in the review of D-26). The repair finds the slot by the same count, not from the record.
- The `epoch` of a ring is incremented at every attach that reuses the ring, whether a record was repaired or not. A new ring starts at 0.
- Regions of other processes (`PeerRegions`): one slot for each region the header lists. A slot is mapped when it is first asked for. A region is looked at again at most once a second, and not only while it is missing: a mapped region whose file is gone, was replaced or was shrunk is dropped or mapped anew. Until `scada_tag_notify` exists (issue P1-07), `scada_tag_status` does this. A mapping is kept until detach, because a reader in a real-time function may still hold it; a region may be mapped anew 16 times, after that it reads as missing until the process attaches again.
- Own and other regions are brought into memory with `madvise` (`MADV_POPULATE_WRITE`, `MADV_POPULATE_READ`, Linux 5.14), which returns an error where touching the pages would end the process with a signal.
- Attach starts again at most 5 times when it finds a RETIRING generation, without waiting: `scada-tagd` switches `current` before it retires a generation (D-27).
- Left to the issue that builds the part: retained values (P1-09); draining the `cmd` queues, and the cursors of a new `proc` region in an existing generation (P1-08); the clock check of contract 13.1 and its field in `scada_status` (P1-06); `mlockall` stays with the process, as the contract says.
- The issue's tests 5, 7 and 8 are tests 7, 9 and 12 of contract 0.3. This issue covers the part of attach in tests 7 (repair, readers keep their mappings, the epoch), 9 (wrong user, symbolic link, base directory), 10, 11 (modes) and 12. `SCADA_E_GAP` in test 7 comes with the rings (P1-07); `SCADA_E_NOT_OWNER` in test 8 with write (P1-06), where the read-only mapping is already in place.
- Test 12 is shown from the side of the file: a header whose layout version is 2 is refused by this library. A library built with another layout version is not built by the tests.
Reason: a private class keeps the layout out of every public header and lets unit tests reach the regions, while the C functions stay a few lines each. Taking the lock first costs nothing and closes the time in which two processes of one name could both repair. A header is the one region every process reads; a bug or a crash of `scada-tagd` must not become a wild read in every service. Keeping replaced mappings is the only way a real-time reader never touches unmapped memory without a lock; the limit bounds what a misbehaving owner can take from its readers.
Consequences:
- Contract text for 1.0 (issue P1-13): the definition of `scada_status`; the return codes above, among them `SCADA_E_LAYOUT` for a header that is not valid; the lock before the own regions; the check of the generation directory; the content checks of own regions; `owner_index` of a queue region; the string slot rule; the epoch at every reuse; the once-a-second look at mapped regions as well as missing ones, and the limit of 16; `MADV_POPULATE` and with it Linux 5.14, below the minimum of 5.16.
- A process that is attached cannot be handed a new uid for `scada-tagd`; the lookup of the user `scada-tagd` happens once, at attach.
- `scada-tag-test-peer` now attaches through the C interface; the integration tests of `scada-tagd` use it as before.
- GoogleTest's death tests and parameterised tests are not used: their macros contain `goto` and `new`, which the banned-construct check reports (D-8, D-10). That a store through a read-only mapping ends the process is therefore not tested; `MappedRegion` maps with `PROT_READ` alone.
- Under user-mode emulation of ARM64 (`qemu-aarch64`), `MADV_POPULATE_READ` on a file shorter than its mapping reports success, so the unit test `MappedRegion.PrefaultFailsWithAnErrorWhenTheFileIsTooShort` fails there. The pipeline runs ARM64 natively (D-13).
- New suppressions: `cppcoreguidelines-avoid-non-const-global-variables` once in `region_file.cpp` (the per-thread error number); in `scada_tag.h`, for the C declarations the contract fixes: `performance-enum-size` twice, `modernize-use-using` three times and `readability-identifier-naming` three times; `readability-identifier-naming` once in `c_api.cpp` (`struct scada_ctx`); `cppcoreguidelines-pro-type-vararg` for `open` once in the test helper; the name of the libFuzzer entry point in `header_region_fuzz.cpp`.

## D-29: Tag read and write: the C interface, the sequence lock in code, the overlay, and how real-time safety is tested
Date: 2026-11-14
Phase / issue: 1, #14
Status: accepted

Context: issue #14 adds `scada_tag_resolve`, `scada_tag_info`, `scada_tag_read`, `scada_tag_read_many`, `scada_tag_write` and the string functions, with the sequence lock of contract sections 6.1, 6.2 and 7 and the overlay of the owner state, and a test that the real-time safe functions make no system call and no allocation. The contract fixes the protocol and the function names. It leaves open what `scada_tag_info_t` holds, what several functions return in which case, what a read gives when an owner died in the middle of a write, how the "pause instruction" is written in a code base that allows no architecture-specific code outside the I/O HAL, and how the instrumentation of conformance test 22 works. The issue names "conformance tests 2, 3, 4, 6 and 13", which are numbers of contract 0.1.
Options, access to the fields of a record: as 64-bit words through a cast, as the contract words it; field by field through `std::atomic_ref`. Options, a record left with an odd sequence number by an owner that is down: `SCADA_E_BUSY` for ever; BAD with OWNER_DOWN and no value. Options, the `down` flag of `scada-tagd` in the overlay: used as a fourth rule; not used. Options, pause: none; `std::this_thread::yield` (a system call); one function that names the instruction. Options, finding system calls: a seccomp filter in the process; syscall user dispatch (x86-64 only); tracing a child process with ptrace. Options, finding allocations: counting in replaced allocation functions; comparing allocator statistics.
Decision:
- The sequence lock is in `src/tag_record.cpp`, the only code that reads fields while another process writes them. Every field of a record and of a string slot is loaded and stored through `std::atomic_ref` with relaxed order, field by field, not as 64-bit words. The loads and stores of `seq` and the two fences are those of the contract, in its order. A read tries 64 times.
- The fences are `fence_release` and `fence_acquire` in `src/shared_memory.h`. In the ThreadSanitizer build they are empty: the compiler refuses `std::atomic_thread_fence` there, and that build runs all atomic accesses in one total order. Because every access is atomic, no access is a data race, ThreadSanitizer reports nothing and no suppression file exists. ThreadSanitizer does not check the order of the accesses; the tests with derived values and the model check of conformance test 4 do. The ThreadSanitizer build is for x86-64 only and does not compile for ARM64, where a lock without its fences would be wrong.
- The pause is `scada::cpu_relax()` in `scada/common/cpu_relax.h`: `pause` on x86-64, `yield` on ARM64, written as a standard `asm` declaration. It is the one place outside the I/O HAL that names a processor instruction; any other target fails to compile.
- At attach the library reads the tag directory through the slot table of every owner, not only of its own, and keeps the type of every slot (1 byte for each tag) and the STRING slots of every owner. A handle is then checked with two comparisons, and a read knows the type without the header. A slot without a valid directory entry fails attach with `SCADA_E_LAYOUT`.
- Overlay: the owner counts as down by the first three rules of contract 10.1, evaluated at every read from the `proc` region of its process. The `down` flag of `scada-tagd` is not used: it is the same judgement made up to one check interval earlier, and a flag left by a `scada-tagd` that has stopped would keep a restarted owner down.
- What a read returns: the last value with quality BAD and OWNER_DOWN added when the owner is down; type of the tag, value 0, times 0, quality BAD and only OWNER_DOWN when the `tags` region is missing, or when all 64 attempts found the record mid-write and the owner is down; `SCADA_E_BUSY` when all attempts found it mid-write and the owner is not down. `age_ns` is never negative. (D-30 adds what the output holds with an error.)
- A tag of another process reads as BAD with OWNER_DOWN until it was resolved in the same context, because resolve is where the regions are mapped (contract 11.2).
- A record is input. `SCADA_E_LAYOUT` is returned when a record does not hold the type of its tag, a quality, only known quality flags, 0 or 1 for a BOOL, or the number of its string slot for a STRING; and when a string slot holds a length above 250.
- Write: `SCADA_E_NOT_OWNER` before the value is looked at; `SCADA_E_TYPE` for another type and for `scada_tag_write` on a STRING tag; `SCADA_E_INVALID` for a quality or flag that is none and a BOOL that is neither 0 nor 1. With `source_time_ns` 0 the source time is the update time and LOCAL_TIME is set. `scada_tag_write_many` checks every pair first and writes all or nothing. The value of a STRING tag counts as changed when its text differs.
- Strings: `scada_tag_write_string` refuses text that is not well-formed UTF-8 or longer than 250 bytes; the check (`src/utf8.h`) has the fuzz target `utf8_fuzz`. `scada_tag_read_string` returns the bytes the owner stored, not NUL-terminated; with a buffer that is too small it returns `SCADA_E_INVALID` and the length. A reader does not check UTF-8. The string functions are not real-time safe, as in the contract.
- `scada_tag_read_many` returns `SCADA_OK` or the code of the first tag that was not read; the status array may be NULL.
- `scada_tag_info_t` is 168 bytes: type, flags, whether the caller owns the tag, owner index, process index, tag name and owner name.
- `scada_status.reserved0` becomes `clock_syscall`: 1 if the name of the kernel's clock source is not one the vDSO reads (`tsc`, `kvm-clock`, `hyperv_clocksource_tsc_page`, `arch_sys_counter`) or one clock read takes more than 200 ns (the fastest of 4 batches of 256 reads). Checked at attach and, until `scada_tag_notify` exists (issue P1-07), at most once a minute in `scada_tag_status`.
- `scada_tag_write_many` is part of this issue although the issue does not list it: contract 0.3 added it after the issue was written, and no later issue names it.
- Conformance test 22: the helper `scada-tag-rt-probe` calls every real-time safe function between two markers. The test runs it as a child process traced with ptrace (`scada/test/syscall_trace.h`, Linux 5.3) and fails on any system call between the markers; the helper counts allocations there in replaced global allocation functions that hand out memory from a fixed block. Two further tests make a system call and an allocation on purpose and expect them found. If the library reports `clock_syscall`, clock reads are not counted. The test is registered only in a native build without a sanitizer.
- Conformance test 2 runs 3 s in the pipeline; `SCADA_CONFORMANCE_SECONDS=600` gives the 10 minutes of the contract.
- The issue's tests 2, 3, 4, 6 and 13 are tests 2, 3, 5 with 6, 8 and 22 of contract 0.3.
Reason: field-wise atomic access gives the same guarantee as the word-wise copy of the contract without a cast, and needs no suppression of a race report. A reader that waited on `SCADA_E_BUSY` for a dead owner would never report it, which conformance test 5 forbids. Tracing a child needs no privilege and no architecture-specific code, and sees a system call made inside the vDSO, which a wrapper around library functions would miss.
Consequences:
- Contract text for 1.0 (issue P1-13): field-wise access in place of "one 64-bit word at a time"; the definition of `scada_tag_info_t` and of `clock_syscall`; the return codes above, among them `SCADA_E_LAYOUT` for a record that is not valid; what a read gives for a missing region and for a record left mid-write by a dead owner; that the overlay uses the first three rules of 10.1 only; that a tag must be resolved in the context that reads it; the rule for the clock check.
- The retry limit of 64 is confirmed in issue P1-12 (contract section 16). Measured here on x86-64 only, release build, 4 processors (2.1 GHz): the reference load for 10 minutes gave `SCADA_E_BUSY` for 22 of 62.0 billion reads by 4 readers, against the criterion of 1 in 1,000,000; one tag written in a tight loop with 4 readers on the same 4 processors, debug build, gave it for about 1 read in 9.
- Not done here: the change entry of a write (issue P1-07 adds it where `write_record` returns that the value changed); conformance test 4, the model check of the sequence lock, for which the pipeline has no tool yet (it has an issue, see D-30). The debug-build check of contract 13.2 was added after the review (D-30).
- Attach reads the whole tag directory: about 1 ms for 50,000 tags.
- New suppressions: `scada-banned` and `cppcoreguidelines-pro-type-reinterpret-cast` once in `shared_memory.h` (`text_at`, the name pool read as characters); in `scada_tag.h`, for the C declarations, `performance-enum-size` five times, `modernize-use-using` twice and `readability-identifier-naming` twice; the magic numbers of the UTF-8 tables in `utf8.cpp` and `utf8_fuzz.cpp`, and the name of the libFuzzer entry point there; `cppcoreguidelines-avoid-non-const-global-variables` three times in the probe; in `syscall_trace.cpp`, `cppcoreguidelines-pro-type-vararg` four times for `ptrace`, `cppcoreguidelines-pro-type-union-access` once and `modernize-deprecated-headers` once for `<signal.h>`; `modernize-deprecated-headers` once in the writer; `concurrency-mt-unsafe` once for `getenv` in `tag_access_integration_test.cpp`.

## D-31: The pause of a tag read on ARM64 is `isb`; no own attempt count and no shorter copy for strings
Date: 2026-11-14
Phase / issue: 1, #40
Status: accepted

Context: D-30 left `yield` as the pause of `scada::cpu_relax()` on ARM64 and asked for measurements on ARM64 hardware: whether 64 attempts of a read last long enough for an owner to finish a write, and the rate of `SCADA_E_BUSY`. The issue asks to decide from the figures whether ARM64 uses `isb`, whether the string functions get their own attempt count, and whether the string copy window is shortened. It forbids clock reads in the retry loop and a change of the limit of 64 for the real-time read before issue P1-12. The session that did the work has no ARM64 machine; the product owner chose the ARM64 runner of the pipeline.
Options, where to measure: the ARM64 runner of the pipeline; the target board, by hand; an emulator (gives no timing). Options, the pause on ARM64: `yield`; `isb`; no instruction. Options, strings: as now; an attempt count of their own; copy only `len` bytes or 64-bit words.
Decision:
- Measured on the pipeline runners with `scripts/measure-seqlock.sh` and the program `scada-tag-seqlock-bench`, in the `perf` build, by the manual job `arm64-measurements`. The figures are in `docs/reports/phase-1.md`.
- ARM64 uses `isb`. With `yield` the 64 attempts took 22 ns on a Neoverse N2, a fifth of one string write (113 ns), and 1 read in 80,625 of 1,000 string tags at 50,000 writes per second gave up. With `isb` they took 0.67 us and 1 read in 54 million gave up, against 1 in 25 million on the x86-64 runner with `pause`. A read of a record nobody writes takes the same time with both (15 ns to 17 ns); only a read that finds a write in progress waits longer, at most 0.67 us before it gives up.
- The build option `SCADA_ARM64_PAUSE` (`isb` or `yield`, default `isb`) is kept, so that a new board can be measured both ways. It is a definition of the whole build. x86-64 ignores it.
- The string functions keep the 64 attempts of the scalar read, and the copy stays as it is: with `isb` the window covers a string write about six times over, and the rate for string tags is below the criterion of the scalar ones.
- The limit of 64 is not changed; P1-12 confirms it. There are no clock reads in the retry loop.
Reason: 64 attempts must outlast the longest write a running owner makes, or a reader reports `SCADA_E_BUSY` while nothing is wrong. `isb` gives ARM64 the window x86-64 has with `pause`, without a clock read and without a second attempt count to keep consistent.
Consequences:
- The reference load (conformance test 2, 600 s, 4 readers, 50,000 tags, 50,000 updates per second) gave `SCADA_E_BUSY` for 0 of 33.1 billion reads with `yield` and 5 of 32.5 billion with `isb` on ARM64, and 0 of 26.1 billion on x86-64: all far below 1 in 1,000,000. On 2 processors 4 readers, 10 owner threads and `scada-tagd` share the cores, so a read that gives up there is an owner preempted mid-write, which no pause covers.
- One string tag rewritten without pause (one write every 195 ns) gives up for almost every read on both architectures: a 103 ns copy does not fit between writes. That is not a load of the reference document and is not addressed here.
- The runners are shared virtual machines with 2 processors, not the target board. The measurement is repeated on the board with the same script when it is available; issue #41 also needs the board.
- The job `arm64-measurements` runs only when started by hand (`workflow_dispatch`). It is not one of the checks of a pull request.

The contract leaves open: what `scada_change` and `scada_sub_stats_t` hold, where a subscription starts, what a ring that is missing, appears or is replaced means for a subscription, what a consumer does with an entry that is not valid, how `scada_tag_notify` knows which rings the calling thread wrote, how many sources a wait set takes, and what makes a waiter on `cycle_seq` ready. Issue #42 asks to decide here whether `scada_tag_notify` takes over the look for missing regions (point 1) and what a ring consumer sees when an owner dies (point 2).
Options, mechanism: shared futex on the read-only mapping (the proposal); one eventfd per ring passed by `scada-tagd` over a Unix socket (the fallback); polling. Options, which rings notify wakes: every ring the process owns; the rings whose first writer is the calling thread. Options, a ring that appears or is replaced: deliver on silently; a gap. Options, an invalid entry: stop at it; skip it with `SCADA_E_LAYOUT`. Options, the waiter thread of a descriptor: one per process; one per wait set that asks for a descriptor. Options, the wake-up latency on ARM64: not measured; measured by the pipeline's native ARM64 runner.
Decision:
- Experiment and mechanism. A wait with `FUTEX_WAIT_BITSET` and no `FUTEX_PRIVATE_FLAG` on a 32-bit word of a read-only `MAP_SHARED` mapping of a region file is woken by `FUTEX_WAKE` on the same word through a read-write mapping of the file at another address, in one process (`Futex.*`) and between processes (`scada-tag-change-ring-integration-test`); `futex_waitv` on several such words likewise. The kernel keys a shared futex by file and offset. A wait compares the word first, so a wake before the wait is not lost (`Futex.AWaitOnAWordThatChangedReturnsAtOnce`). Results are below. The mechanism of contract 8.4 is kept; the eventfd fallback is not built.
- The word is the low 32 bits of `write_seq` (the targets are little-endian, so it is at the address of the field; `static_assert` in `src/futex.h`) and `cycle_seq`. A consumer waits with the low 32 bits of its cursor as expected value and an absolute `CLOCK_MONOTONIC` deadline; the owner wakes all waiters. Every wait is cut into slices of at most 100 ms, after each of which the ring is looked at again (contract 8.4). A timeout is from 0 ms; there is no wait without one.
- The change entry is appended in `write`, `write_many` and `write_string` when `write_record` reports a change, after `seq` is even again (contract 6.1), with the stored fields. The append uses the orders and fence of contract 8.1, field by field through `std::atomic_ref` as the sequence lock does (D-29). It is real-time safe; conformance test 22 covers it, since the probe writes a tag.
- `scada_tag_notify`: the first thread that writes the tags of an owner is now recorded in every build, not only in the debug check of contract 13.2 (a relaxed load per write; a compare-and-swap once). Notify wakes each ring whose recorded writer is the calling thread and whose `write_seq` changed since its last wake (one `FUTEX_WAKE` each), increments `cycle_seq` with an atomic add (several threads may notify) and always wakes its waiters, then looks again for missing regions and repeats the clock check, as `scada_tag_status` does. This settles point 1 of issue #42.
- `scada_change` (32 bytes): handle, type, quality, flags, value, source time, `update_mono_ns`, the stored fields (with the overlay of contract 6.2 while the owner is down, D-33). `scada_sub_stats_t` (40 bytes; 48 since D-33): changes received, gaps, entries lost to overruns, entries refused, epoch, owner and process index.
- A subscription starts at the end of the ring. `SCADA_E_GAP` is returned once for each of: an overrun (contract 8.2, `w - cursor >= capacity`, so a consumer may fall `capacity - 1` entries behind), a changed epoch, and a ring that appears, disappears or is mapped anew (a file replaced). Opening a subscription to a missing ring succeeds. The epoch is read before `write_seq`, so a restart between the two loads gives one gap too many and never one too few. After a gap the cursor is the current `write_seq` (contract 8.3).
- An entry that is not a valid change of a tag of the owner (handle, type, quality, flags, BOOL 0 or 1, STRING slot number) is counted and skipped with `SCADA_E_LAYOUT`. A ring header with another capacity than the owner table gives `SCADA_E_LAYOUT` at open and at every `scada_sub_next`.
- Wait sets hold up to 127 sources (the kernel's 128 words for one wait, less the stop word of the thread). A subscription is in at most one wait set; closing it takes it out, and destroying the set lets go of its subscriptions. A cycle source is ready when `cycle_seq` differs from the count the previous return of `scada_waitset_wait` saw.
- `scada_waitset_fd` starts one thread for that wait set (contract 8.4 says "one waiter thread in that process"; a process with one wait set has one). The thread waits with `futex_waitv` on the sources and on a private stop word, compares them with what it saw last (mapping, epoch, word) and writes to a non-blocking, close-on-exec eventfd when any changed. Its first view is taken before the look at what is ready already, which is signalled at once, so no change between the two is lost. Sources cannot be added once it runs.
- Point 2 of issue #42, an owner that dies: settled by the product owner, see D-33.
- The wake-up latency is measured by `scada-tag-wake-perf-test`: a writer process writes one tag every 2 ms with notify, and this process, blocked in `scada_sub_next`, takes `CLOCK_MONOTONIC` on return minus the entry's `update_mono_ns`, over 2,500 changes. It fails on x86-64 at a 99th percentile of 1 ms or more. Exception to D-13: both `build and test` jobs run it on the `release` build with `SCADA_PERF_REPORT_ONLY=1`, which prints the figures and gates on nothing, because the ARM64 runner is the only ARM64 machine the project has.
Reason: the futex needs no help from `scada-tagd` and passes nothing between processes, which keeps `scada-tagd` out of the data path (contract 17, item 3). Waking only the rings of the calling thread keeps the cost of notify proportional to what that thread wrote. A ring that appears or is replaced may hold changes the consumer never saw, so it must resynchronise, as after an overrun. Skipping an invalid entry keeps one damaged entry from stopping a consumer for good, while the return code still tells it.
Consequences:
- Results, x86-64 (container, Linux 6.18, 4 processors, Xeon 2.1 GHz): all `Futex.*`, `Changes.*` and `ChangeRingProcesses.*` tests pass in the dev, release, asan-ubsan and tsan builds. Wake-up latency between two processes, `perf` preset, 2,500 changes, two runs: median 61 µs both; 99th percentile 152 µs and 173 µs (target: below 1 ms); maximum 2.4 ms and 10.6 ms. The dev build gave median 56 µs, 99th percentile 149 µs. The maximum is a scheduling delay of the machine, which the 99th percentile target allows for.
- Results, ARM64 (the pipeline's native runner `ubuntu-24.04-arm`, 2 processors, run 43618327669 of pull request #45): the same tests pass in the `dev` and `release` builds. Wake-up latency, `release` build, 2,500 changes: median 8 µs, 99th percentile 17 µs, maximum 690 µs. The step "Wake-up latency, reported only (release)" of `build and test (ARM64)` prints it on every run.
- Contract 0.5: section 8 (when an entry is appended, entries are input, gap causes, epoch before `write_seq`, start at the end), 8.4 (the mechanism specified), 13 (`scada_change`, `scada_sub_stats_t`, timeouts), 16 (settled). Layout version 1 is unchanged.
- Issue #39 (model check, conformance test 4) covers the ring of `src/change_ring.cpp`.
- Not done here: `scada_waitset_add_queue` and the wake of queues (P1-08); `scada_proc_resolve` and `scada_proc_status`, which a consumer of `cycle_seq` would use to find a process by name; until then `scada_tag_info` gives the process index of a tag's owner.

## D-33: A change ring reports its owner going down and coming back
Date: 2026-11-14
Phase / issue: 1, #15 and #42 (point 2)
Status: accepted

Context: a dead owner writes no change entry. A consumer that only follows the ring (alarms, historian, WebSocket feed) then keeps the last good value, which is the wrong direction for a control system to fail in. D-32 documented this and left the choice to the product owner in issue #42; the product owner asked for the gap.
Options: documentation only (D-32); a gap when the owner's process goes down and when it comes back; a special change entry written by `scada-tagd`, which would make it a writer of rings it does not own.
Decision:
- A subscription evaluates the owner's process by the three rules of contract 10.1 at every look, as the read overlay does, and returns `SCADA_E_GAP` once when the result changes from not down to down and once when it changes back. The cursor and the epoch then move to the end of the ring: the reads after the gap supersede what the ring held. The state at `scada_sub_open` is the starting point, not a change.
- While the owner's process is down, an entry that still arrives is delivered with the overlay of contract 6.2: quality BAD, OWNER_DOWN added. An owner whose heartbeat stopped can have threads that still write; their values must not reach a consumer as good.
- A restart gives two gaps to a consumer that looked while the owner was down, one to a consumer that did not. A ring that appears or is replaced at the same look as a change of the owner state gives one gap, not two.
- A wait looks again at least every 100 ms, and wait sets and their descriptor thread compare the owner state too, so a waiting consumer gets the gap within the owner's heartbeat timeout plus 100 ms, and at once after a clean stop.
- `scada_sub_stats_t` gets `owner_changes` and `owner_down` and grows from 40 to 48 bytes. Nothing had been released with 40 bytes; contract 0.5 says 48.
- `scada_sub_stats_t.last_gap` tells why the last gap came: `SCADA_GAP_OVERRUN`, `_RESTART`, `_RING`, `_OWNER_DOWN` or `_OWNER_BACK` (0 before the first). Since a gap now has two meanings (data lost; owner state changed), an alarm system needs to tell them apart without inferring it; the action stays the same, a read of the tags. When the owner's state changes at the same look as its ring appears or is replaced, the owner's reason is given, because that is what an alarm acts on. It takes one of the three reserved bytes; the size stays 48. Added after a review of this decision with the product owner.
Reason: a consumer of the ring learns of a dead owner from the ring, with the code it already has to handle, and the values it then reads are BAD with OWNER_DOWN. `scada-tagd` stays out of the data path.
Consequences:
- Conformance test 7 counts the second gap of a consumer that saw the owner down (contract 0.5, section 15).
- `scada_sub_next` reads the owner's `proc` region and the monotonic clock at every look: two loads and one clock read from the vDSO.
- Tests: `Changes.AnOwnerThatStopsGivesAGapAndAnotherWhenItIsBack`, `AChangeOfAnOwnerThatIsDownComesAsBad`, `AnOwnerDownAtOpenGivesNoGapUntilItComesUp`, `ABlockedConsumerLearnsThatTheOwnerStopped`, `AWaitSetWakesWhenTheOwnerStops`; across processes `ChangeRingProcesses.AKilledOwnerGivesAGapWithinItsHeartbeatTimeout`.

## D-34: The clock check compares with a raw system call; a heartbeat time in the future is bounded by the timeout
Date: 2026-11-14
Phase / issue: 1, #41
Status: accepted for the code; the run on the target ARM64 board is still open

Context: D-29 judged whether clock reads are system calls by the name of the clock source and a fixed limit of 200 ns for one read. The review of P1-06 (D-30) found that an ARM timer erratum workaround makes the vDSO fall back to the system call while the name stays `arch_sys_counter`, and that such a call can take under 200 ns on a fast core, while a slow core can take more than 200 ns in the vDSO. `proc_liveness` counted any heartbeat time ahead of the reader's clock as alive. The issue leaves open how much faster than the system call a read must be, and how far ahead a heartbeat time may lie.
Options, the time signal: a fixed limit, as before; a ratio to the time of a raw `clock_gettime` system call, timed on the same machine at the same moment. Options, the ratio: 1 (any speedup); 2; a larger factor. Options, the bound for a time in the future: a new constant; the heartbeat timeout of the process; a fraction of it.
Decision:
- `clock_syscall` is 1 when the clock source name is not one the vDSO reads, or when one library read of `CLOCK_MONOTONIC` takes more than half the time of one raw `syscall(SYS_clock_gettime, CLOCK_MONOTONIC)` (`CLOCK_READ_SPEEDUP` = 2). Both are the mean of the fastest of 4 batches; 256 reads per batch for the library, 64 for the system call. The fixed limit of 200 ns is gone. An empty name decides nothing, as before; a refused system call (a seccomp filter) leaves only the name to decide.
- A heartbeat time more than `heartbeat_timeout_ms` ahead of the reader's clock is down (`heartbeat stale`), in the library and in `scada-tagd` alike; exactly the timeout ahead is not. Contract 0.6 says so in section 10.1, and section 3.4 forbids a private time namespace.
Reason: a vDSO that falls back to the system call does the call and more, so it is never faster than the raw call, while a real vDSO read is several times faster on every core: the ratio holds on slow and fast cores where a fixed limit does not. A factor of 2 leaves room for noise in either direction. Measured on x86-64 here (virtual machine, `tsc`, 4 processors): library read 36 ns to 44 ns, raw system call 163 ns to 170 ns, a factor of about 4.5. A heartbeat can lie ahead of a reader's clock only by the time the reader spends between reading its clock and the heartbeat, which is microseconds; the timeout is the bound that needs no new setting, and a reader delayed longer than it sees the process down for a moment, which is the safe direction.
Consequences:
- The check takes about 0.1 ms, under 1 ms on the supported targets, at attach and once a minute, from `scada_tag_status` and `scada_tag_notify`. A real-time task that calls `scada_tag_notify` at the end of a cycle therefore spends about 0.1 ms in it once a minute, against a few tens of microseconds before.
- Not done in this pull request, so issue #41 stays open: running the check and conformance test 22 on the target ARM64 board, and on a machine booted with the vDSO clock disabled, and recording the figures here. The pipeline's ARM64 runner is a virtual machine. The unit test `ClockCheck.ASystemCallTimedAgainstItselfIsOne` stands in for the second: it times the raw system call against itself, which is what such a machine measures.
- In the ThreadSanitizer build the C library clock read is intercepted and takes about 100 ns against about 195 ns for the raw system call, at the limit, so the check can give 1 there and differ between two attachments. The unit test `TagAccess.TheStatusReportsTheClockCheck` therefore checks that one attachment reports the same result twice, not that two attachments agree. Conformance test 22, which expects 0, runs only in a native build without a sanitizer (D-29).
- New suppression: `cppcoreguidelines-pro-type-vararg` once in `clock_check.cpp`, for `syscall`.
- A reader preempted between its clock read and the heartbeat read for longer than the timeout sees a running owner down for that read; this includes a reader preempted inside one `scada_tag_read_many`, which reads the clock once for the whole call (contract 13). Intended, the safe direction; seen in issue #62 with a reader held 3.2 s and 4.4 s inside one call of 500 tags on an overloaded machine (D-50).

## D-36: A process records its late heartbeats; the heartbeat is safe from several threads
Date: 2026-11-15
Phase / issue: 1, #42 (point 4)
Status: accepted

Context: a reader judges liveness itself at every read (contract 10.1), while `scada-tagd` checks every `heartbeat_check_ms`. A heartbeat gap longer than the timeout and shorter than the check interval turns tags BAD with OWNER_DOWN and gives ring consumers a gap (D-33), and no "process down" record exists. Issue #42 asks to make such a transient traceable. D-35 left the choice to the product owner, who had it decided by a committee of a C++, a Linux systems and a SCADA architecture reviewer and accepted its recommendation. The committee was unanimous in both rounds. It also found that `scada_tag_heartbeat`, which contract 13.2 makes safe from any thread, loaded and stored the heartbeat counter and stored the time unconditionally: two threads could lose a count and publish an older time over a newer one, which shows a live process down to readers.
Options: A, `scada-tagd` infers gaps from the count and time it samples at each check; B, the owner counts its late heartbeats in reserved bytes of `ProcHeader` and `scada-tagd` logs them; C, close the point with a reason; a counter in `scada_proc_status` or a system tag (left for later). For the thread defect: fix it here; a separate bug issue first; narrow 13.2 to one thread.
Decision:
- B. `ProcHeader` takes `late_beats` (u32, offset 28), `longest_gap_ns` (i64, 32) and `last_late_mono_ns` (i64, 40) from its reserved bytes; 16 stay reserved; size and alignment stay 64. Contract 0.8, layout version 1.
- The writer (`OwnProcRegion::heartbeat`): the counter is a relaxed `fetch_add`; the time is advanced by a compare-and-swap (release on success) only when it is later than the published one, so it never goes back and a time that is not newer is not published. The thread that publishes owns the gap since the previous time: it raises `longest_gap_ns` (relaxed compare-and-swap), and for a gap strictly longer than the timeout raises `last_late_mono_ns` and increments `late_beats`. "Strictly" is the boundary of `proc_liveness`: a heartbeat exactly as old as the timeout is not stale. Real-time safe: a few atomic operations, no system call; a retry only when another thread of the process published meanwhile.
- The first heartbeat of a life (`first_heartbeat`, in attach) stores the time unconditionally and is not measured: the gap since a previous life is a restart, and a time a previous life left ahead of the clock must not hold back this one. The figures of a reused region are kept, so `scada-tagd`, which keeps its mapping across a fast restart, never sees the count go back; a new region starts at 0.
- The timeout is the process's own `heartbeat_timeout_ms`, given to the region at attach. `scada-tagd` counts its own late heartbeats too: while they lasted, readers saw `SCADA_E_TAGD_DOWN`.
- The reader (`GenerationHost::check`): loads `late_beats` with acquire, then the gap fields, for every process including itself, and reports the growth since the previous check (modulo 2^32). The first sample of a mapping is a baseline: reported only if it is not 0, and marked. `scada-tagd` logs `heartbeat late` at WARNING, also when a down or up change of the same process was logged in the same check, because only this record carries the gap; a baseline is logged once at INFO as `heartbeat late before this check`. At most one record per process and check.
- The figures are self-reported and a lower bound: a gap is measured between two clock readings, not between the moments the heartbeats were published, so a heartbeat preempted between its clock reading and its compare-and-swap is seen late by readers for longer than it records, and may record nothing. A process that hangs for good records nothing; `scada-tagd` reports it down. `longest_gap_ns` is the maximum since the region was created, not the gap of the logged record. `last_late_mono_ns` is a maximum too (a compare-and-swap), so that two late threads cannot move it back; the increment of `late_beats` is acq_rel. Changed after a committee review of the pull request relayed by the coordinating session.
- The fields are for diagnosis only and are never used to judge liveness; they are input to their readers.
- The thread defect is fixed in this change, because the same function is rewritten; contract 13.2 keeps "safe from any thread" and says that the published time never goes back.
- A is rejected: the writer stores the count before the time, so a sample can pair a count with the time of the beat before, and two clean gaps then look like one late one; and with several heartbeats between two checks, the normal case, it proves nothing.
Reason: only the owner sees every gap, and the comparison with its own previous time is cheap and exact. The record then matches what readers saw, so a BAD transient in the historian or an alarm can be traced to the process and the moment.
Consequences:
- Contract 0.8, sections 10, 10.1 and 13.2, with a migration note: a 0.7 library leaves zeros, which read as "none recorded".
- Tests that fail without the change: `LateHeartbeat.*` in `proc_region_test.cpp` (strict boundary, longest gap, a time that is not newer, the first heartbeat after attach, several threads), `Host.AHeartbeatGapBetweenTwoChecksIsReportedAsLate` and `Host.LateHeartbeatsFoundAtStartAreABaseline`, and `TagdService.ALateHeartbeatIsLogged` with real processes; `scada-tag-test-peer` takes `late=<ms>` for it.
- Follow-ups, not done here: the figures in `scada_proc_status` or a system tag (with `scada_proc_status`, which no issue has built yet, D-32); a system alarm or journal record for late heartbeats (alarm service); a count of fast restarts, which a reused region hides from `scada-tagd` (systemd's restart count and journal trace them meanwhile). Done in D-47: the journal hook, a rate limit and the count of lives (`starts`); the log field is `LAST_LATE_MONO_US` in µs, the shared-memory field `last_late_mono_ns` stays in ns.
- The CAS is a load-linked/store-conditional loop on ARMv8.0 without LSE: lock-free, not wait-free; only threads of the same process contend.

The seqlock test is two string writes (`seq`, the slot, the record fields, `seq`) against one read attempt; the ring test is three appends to a ring of capacity 2, the third overwriting slot 0, against one read at cursor 0. Two locations stand for the fields of a record and its slot (a mixed copy of more fields contains a mixed pair), two for an entry. The owner's relaxed loads of its own `seq` and `write_seq` are written as the constants they give, since it is their only writer: with them, herd7 had 3 million candidate executions for the first version of the seqlock test and did not finish in 120 s on the runner. The condition is a copy the library would accept that is not one write whole.
- `tests/model/model_check.py` expects "Never" for each test and "Sometimes" for each of four copies with one ordering taken away: `DMB ISH` and `DMB ISHLD` replaced by `NOP`, `STLR` by `STR`, `LDAR` by `LDR`. The issue asks this for the two fences; the two other orderings are part of the same protocol and cost nothing to check.

Calls of functions of the same object file are followed: GCC 13 at -O2 does not inline `copy_fields`, `store_fields`, `changes_record` or `ring_header`. Paths that end in `panic`, `std::__glibcxx_assert_fail` or `__stack_chk_fail` are left out: they do not return and publish nothing; GCC repeats the start of a string write on such a path. It runs as `scada-model-code-shape-test` (label `unit`) in ARM64 builds with optimisation and without a sanitizer, so in the `release` tests of `build and test (ARM64)`. `scada-model-code-shape-self-test` runs it on a fixture of Clang 18 output on every host, as compiled and with each ordering edited out of each function.
- The model check is the test `scada-model-check`, label `model`, test preset `model` (no tests found is an error). It is registered when herd7 is found; `-DSCADA_REQUIRE_HERD7=ON` stops the configuration without it. The pipeline job `model check` builds herd7 from the tag in `setup-build-machine` (input `herd7`, the only place that names a package manager, D-13) and runs `ctest --preset model`.
Reason: `aarch64.cat` is written for herd7, and Arm validates its architecture model with it. GenMC's licence is not allowed; Dartagnan would bring a Java runtime to the build machine for the same model. A model of the instructions is the one that says something about ARM64 units; a model of C++ would leave the compiler's mapping unchecked. Without the disassembly check an edit that drops a fence from the C++ would leave the model passing, which is the failure the issue was opened for.
Consequences:

One run of the seqlock test takes 44 s to 48 s, of the ring test 8 s to 10 s; the test takes 275 s. `scada-model-code-shape-test` passes on the GCC 13.3 `release` build of the ARM64 runner. - Not seen by the disassembly check (as first written; D-39 closes the two gaps of addresses): which register holds which field. ## D-40: Reliable queues: the C interface, record checks, ids, expiry answered by the library, the drain at attach, counts, and cursors out of range
Date: 2026-11-15
Phase / issue: 1, #16
Status: accepted. Expiry (B), the conditions on it, the counts, the tag-set pair and a queue region recreated inside a generation were decided by the committee of the lead session (C++, SCADA architecture and Linux experts; the owner delegated contract and command-handling decisions to it) on 2026-11-15.

Context: issue #16 (P1-08) adds `scada_queue_open`, `scada_queue_post`, `scada_queue_next`, `scada_queue_ack`, `scada_queue_close`, the records of contract 9.4, request ids, `FULL`, `PEER_DOWN` and at-least-once redelivery, and `scada_waitset_add_queue`, which D-32 left to this issue. D-28 left the drain of the `cmd` queues and the cursors of a new `proc` region to this issue too. The acceptance names "conformance test 10", the number of contract 0.1; it is test 16 of the current contract, and tests 17 to 19 cover the same section (confirmed by the lead session). The contract leaves open: the numbers of `EventRecord.kind`; what a record must hold to be valid; who sets `posted_mono_ns`; who answers an expired request; what a consumer does with a record that is not valid and with a cursor out of range; where "reports how many records were skipped" reports; which result queue answers a `cmd` queue; what `next` does with a record that was not acknowledged; and a queue with one process at both ends.
Options, the copy of a record: field by field as the rings (D-32); as 64-bit words. Options, `posted_mono_ns`: set by the poster; set by the library at post. Options, the answer EXPIRED: by the driver framework, the library delivering every request (A); by `scada_queue_next`, which never returns an expired request (B). Options, a record that is not valid: stop at it; pass over it with `SCADA_E_LAYOUT`. Options, a cursor out of range: reject it and stop; set it to `write_seq` and go on. Options, the counts: a log line; fields added to `scada_status`; a statistics call per queue. Options, a queue whose producer and consumer are one process: the first open takes one side; refused by the tag-set builder.
Decision:
- C interface in `scada/tag/scada_tag.h`: the five queue functions, `scada_queue_stats`, `scada_waitset_add_queue`, and the records as `scada_event_record` (256 bytes), `scada_write_request` (64) and `scada_write_result` (32), byte for byte the structures of `layout.h` (`static_assert` in `c_api.cpp`), with their enumerations `SCADA_EVENT_*`, `SCADA_OP_*`, `SCADA_SOURCE_*` and `SCADA_RESULT_*`. The logic is the private class `Queue` (`src/queue.h`) and the queue parts of `Attachment` (`src/queue_access.cpp`); the shared memory is reached only through `src/queue_region.h`.
- `scada_queue_open` opens the side the calling process has in the queue table. `SCADA_E_NOT_OWNER` if it has none, `SCADA_E_BUSY` for a second open of the same side in one context. The regions a side needs are mapped and brought into memory at attach (the drain needs them) and again at open; none in `post`.
- A record is copied as 64-bit words with relaxed atomic loads and stores; `write_seq` (release at post, acquire at take) and the cursor (release at ack or take, acquire at post) order them, so no fence is needed. All three record sizes are multiples of 8. Cursor and `write_seq` are loaded once and decided on as copies.
- `EventRecord.kind`: 1 ALARM, 2 COMMAND, 3 AUDIT, 4 SYSTEM, in the order of the contract.
- Checks of a record, at post (`SCADA_E_INVALID`) and on the copy when it is taken: event kind and `payload_len` at most 232; request `operation` and `source` of their enumerations, `value_type` BOOL, INT64, UINT64 or FLOAT64 (STRING cannot be commanded, contract 9.4) or 0 with value 0 for CANCEL and READ_NOW, a BOOL value 0 or 1, `user_id` 0 for AUTO and REMOTE (and not 0 for OPERATOR, added by D-44), `select_request_id` set exactly for OPERATE and CANCEL, reserved fields 0; result `status` 1 to 7, reserved fields 0. The target handle is not checked: it is the driver's to judge. When a record is taken its id must also be its position (`seq`, or `request_id` = `(queue_id << 48) | position`); a result carries the id of the request it answers and is not compared. A `cmd` queue whose `write_seq` reaches 2^48 refuses further posts with `SCADA_E_FULL` (about 9 years at 1,000,000 posts a second).
- The library sets `posted_mono_ns` to the time of the post, which keeps a caller's bug from defeating the lifetime limit. It is not a security boundary: the producer maps its region read-write. The consumer therefore bounds the lifetime on its own clock (next point).
- Expiry, option B (committee, unanimous): `scada_queue_next` on a `cmd` queue never returns a request that must not be executed; it answers it EXPIRED in the answer queue and takes the next. Conditions of the committee, all met:
  1. The clock is read after `write_seq` was loaded and the copy is judged, never the mapped record. A request must not be executed when its expiry is not after now, it was posted after now, it expires before it was posted, its lifetime is longer than 60 s, or its expiry lies more than 60 s ahead of now (`request_expired`, without overflow for any field values). A post that fails the same check is refused with `SCADA_E_INVALID`; this is stricter than the decision text and was accepted by the committee at the review of PR #56.
  2. The cursor moves on first, then EXPIRED is posted. A crash in between loses the answer (contract 9.2 allows it; the requester sees the request expire), and never gives the request again or EXPIRED followed by ABORTED.
  3. `scada_queue_next` never blocks or fails on the answer queue: an answer that cannot be posted (full, requester down, no answer queue, or another thread bound to it) is dropped and counted (`answers_dropped`), and the request is still not delivered. One call passes over at most a queue's capacity of expired requests before it looks at its deadline. The internal post makes no wake system call; `scada_tag_notify` or the 100 ms slice of the requester's wait delivers it. With timeout 0 `scada_queue_next` makes no system call (in the probe of conformance test 22).
  4. One thread posts to a queue, in every build: the first thread that posts (or, for the answer queue of a `cmd` queue, the first that calls `scada_queue_next` on it) is bound for the context and queue, as D-32 does for tag writers. A build without NDEBUG stops the process on a second thread; a release build refuses the post with `SCADA_E_INVALID` and writes nothing. A queue stays bound while any side that posts to it is open in the context, its producer side and, for an answer queue, the side that consumes its `cmd` queue, whichever thread closes a handle; when the last of them closes, the binding is cleared (review of PR #56: a refused thread that closed its handle released the other thread's binding and could then post; and a binding released only by its own thread stayed until detach when another thread closed the last side). The internal answer of `scada_queue_next` takes the binding without the debug stop: when another thread holds the answer queue, the answer is dropped and counted in every build, since that is the library's own post and not a misuse by the caller. The answers of the drain at attach do not bind a thread. The rule, per context and queue, and what keeps it: a thread binds a queue only through an open side that posts to it, between that side's open and its close (`scada_queue_post` on its producer side, `scada_queue_next` on the side that consumes its `cmd` queue); the binding is cleared only by the close of such a side, and only when no such side is left open. Open (`claim_queue`) sets its side's bit under one mutex of the context; close (`close_queue`) clears its bit, tests the other sides and clears the binding under the same mutex, in one step, so an open and a clear are ordered: either the clear comes first and the new side binds afresh, or the close sees the new side open and leaves the binding (review of PR #56: with the test and the clear in two steps, a side opened between them lost the binding it had just taken). The binds in `post` and `next` are a compare-and-exchange from no thread to the calling one, without the mutex; a bind happens before its side's close takes the mutex, so the mutex orders it before any clear. `scada_tag_notify` only reads the binding. The drain runs inside attach, before the context is returned, when no handle and no other thread can use it. `scada_tag_detach` comes after every queue is closed, as the header requires. Real-time code takes no lock: `post` and `next` never take the mutex. A side that opens while another side of the queue is open and bound to another thread is refused when it posts, until both have closed. Tests: `Queues.AQueueStaysBoundWhileASideOpensAsAnotherCloses` (50,000 rounds of an open, a bind and a check against a thread that opens and closes the other side; fails without the single step), `Queues.ClosingAHandleDoesNotUnbindAnotherThread`, `AnAnswerQueueIsFreeOnceItsLastSideIsClosedByAnyThread` and `AnAnswerQueueIsFreeWhenItsSidesCloseInEitherOrder` (each fails without its fix; the threads stay alive until the check, because a thread that has ended may leave its thread mark to a new one), `TheDrainAtAttachBindsNoThread`, `AnAnswerOfAnUnboundThreadIsDroppedAndCounted`, `ASecondPostingThreadIsRefusedInAReleaseBuild`, and with real processes `QueueProcesses.ASecondPostingThreadIsStoppedOrRefused`, which expects the stop in a debug build and the refusal otherwise.
  5. Exactly one answerer per request: the library answers what it does not deliver, the driver what it received. The driver checks `expiry_mono_ns` again right before it acts on the device.
  The answer queue of `cmd.<x>` is the RESULT queue `result.<x>` whose producer and consumer are the consumer and producer of the `cmd` queue. Without one the answer is dropped; this extends contract 9.2, which names only "full or requester down".
- EVENTS and RESULT: `scada_queue_next` gives the record at the cursor until `scada_queue_ack` moves the cursor on; a second `next` without an ack gives the same record. `scada_queue_ack` without a record waiting, on a `cmd` queue or on the producer's side is `SCADA_E_INVALID`. CMD: the cursor moves on after the copy and before `next` returns.
- A record that fails its checks is passed over with `SCADA_E_LAYOUT`, as an invalid change entry (D-32), and counted (`invalid`). A cursor out of range (`r > w` or `w - r > capacity`) is rejected and not followed (confirmed by the committee): the consumer gets `SCADA_E_LAYOUT` at every call and consumes nothing, the producer gets `SCADA_E_PEER_DOWN`, and each look is counted (`out_of_range`). The library does not log; the process logs once per change of that state with the queue name, the counts and what it knows. A stopped queue does not make its consumer spin (review of PR #56): `scada_queue_next` waits out its timeout before it returns `SCADA_E_LAYOUT`, and the queue gives a wait set no futex word, so the set sleeps in slices of 100 ms (a wait with the cursor as expected value would end at once, because `write_seq` never equals it). `Queues.AWaitOnAStoppedQueueDoesNotSpin` bounds the CPU time of both waits; without the fix a wait of 300 ms used 300 ms of CPU. Recovery is a generation change or a reboot. With "no audit, no action" this fails safe: actions that need the queue are refused.
- Attach (contract 9.2 and 11.2, step 5), before the state becomes RUNNING: if `proc.<process>` was created, the cursor of every queue the process consumes is set to the queue's `write_seq` and those records count as `skipped`; every request still in a `cmd` queue of the process is answered ABORTED and passed over (`aborted`, and `answers_dropped` when the answer cannot be posted). A `cmd` cursor out of range is left as it is: setting it to `write_seq` could restart request ids after a recreated queue.
- A queue region recreated inside a generation (committee, 2 to 1: the queue stays stopped; a producer starting at the consumer's cursor, or a consumer resetting its cursor, were rejected because records accepted with `SCADA_OK` could be skipped uncounted and ids could repeat). It happens when the file under the real name is shrunk, damaged or removed and the producer creates it anew; a crash during creation cannot cause it (contract 3.2). The context remembers the first mapping it sees of each queue it consumes (at attach, open and every look); a different mapping later, or none, makes the queue dead in that context whatever the arithmetic of cursor and `write_seq` says. This covers the case the range rule cannot see, a cursor at or below the new `write_seq` (checked on request of the committee, and confirmed: it lost accepted records silently and repeated ids). The consumer then stores an all-ones cursor, so that the producer gets `SCADA_E_PEER_DOWN` by the rule of 9.1, also after either restarts; `replaced` counts it. A producer counts `replaced` when attach created its queue file while the consumer's cursor was not 0; the process logs that as a WARNING. The queue stays dead until a tag-set change or a reboot: a restart of `scada-tagd` reuses the generation (contract 11.1, step 2). Candidate fix: a base sequence in `QueueHeader.reserved` (issue #53). Residual gaps until then: posts between the recreation and the consumer's next look (up to about 1 s) are accepted and lost, and a consumer that was not attached during the recreation cannot tell the new file from the old one.
- Counts (committee, overturning the first version, which grew `scada_status`): `scada_status` stays 32 bytes. `scada_queue_stats` fills a `scada_queue_stats_t` for one side of a queue in its context, since attach, so the drain is visible after open: `posted`, `delivered`, `expired`, `aborted`, `skipped`, `answers_dropped`, `invalid`, `out_of_range`, `replaced`, the queue id, its kind, and the side (80 bytes). For an events queue `skipped` counts lost audit records. Counters are relaxed atomics, so the call is safe from any thread; `post` adds one relaxed increment.
- `scada_tag_notify` wakes, besides the rings, every queue the calling thread posted to since its previous call (one `FUTEX_WAKE` on the low 32 bits of `write_seq`); a consumer waits with the low 32 bits of its cursor. A wait set takes queues as sources, ready when the cursor is not at `write_seq` and the pair is in range; its descriptor thread watches `write_seq`.
- An observer context (D-42, contract 11.4 item 4) has no side in any queue: `scada_queue_open` returns `SCADA_E_NOT_OWNER` for any name before it looks anything up or maps anything (an observer has no queue table, so the lookup would give `SCADA_E_NOT_FOUND`). Post, ack and `scada_waitset_add_queue` then have no handle and refuse NULL with `SCADA_E_INVALID`. Test: `Observer.HasNoQueue`, which also checks that the observer's queue calls add no mapping and change no file.
- The tag-set builder refuses a queue whose producer and consumer are the same process: contract section 9 has two processes, and its side could not be told at open. `scada_queue_open` refuses such a queue from a header too.
Reason: the words need no cast and no fence beyond the release and acquire the protocol has. An expired command that never reaches protocol code cannot be executed late by a driver; contract 9.2 already has the library answer ABORTED at attach; conformance test 17 must pass in phase 1 without a driver framework; audit is unchanged because the requester journals the command and its outcome (reference 8.2, steps 8 and 10). Passing over a damaged record keeps one record from stopping a queue for good; a cursor out of range says that the two sides no longer agree on what was delivered, and following it could lose or repeat records. `scada_status` is allocated by the caller without a size field, so growing it overruns older callers, and issue #19 depends on its size.
Consequences:
- Contract: section 9 and 9.4 (the points above), 16 (open points), 17 (items below); layout version 1 is unchanged and no structure in shared memory changed.
- Phase 2: a driver never sees an expired OPERATE or CANCEL, so drivers time out selections themselves. Reference 6.1 puts command queue handling in `libscada-driver`; the refusal of expired requests now sits in `libscada-tag` (contract section 17).
- Tests: conformance tests 16, 17 (the library's part) and 19 in one process (`Queues.*`) and with real processes (`scada-tag-queue-integration-test`); test 18 in one process. One million records pass between two processes in about 3.5 s on the x86-64 container (dev build). `scada_queue_post` and `scada_queue_next` with timeout 0 are in the probe of conformance test 22. ## D-41: The simulator writer `scada-sim`: one layout for file and processes, owners as threads, patterns from the write count, pacing by 1 ms ticks
Date: 2026-11-15
Phase / issue: 1, #18
Status: accepted

Context: issue #18 asks for `scada-sim`: a configurable number of owner processes writing tags at a set rate with selectable patterns (ramp, sine, random walk, step), a self-checking pattern for torn reads, and the tag-set file for a given tag count, used by the conformance and performance tests. Reference 15.3 makes simulators part of the deliverable. The issue leaves open how a process finds its tags, what "owner processes" means since owners are threads (D-24), how each pattern is defined, how the rate is shared and paced, and whether the simulator is installed.
Options, how a simulator process finds its tags: read the tag-set file; a naming rule computed from the same options as the file. Options, owners: one process per owner; threads of one or more processes. Options, values: functions of the clock; functions of the write count. Options, random walk: a generator per tag; a hash of seed, tag and count. Options, pacing: a sleep per update; per 1 ms tick, what is due by then. Options, the existing `scada-tag-test-writer`: keep it as the load writer; replace it by `scada-sim`.
Decision:
- `libscada-sim` holds the logic (`Layout`, patterns, tag set, the command); `services/scada-sim` is the thin executable. The two commands `tag-set` and `run` take the same layout options (`--prefix`, `--processes`, `--owners`, `--tags`, `--pattern`) and compute the same names: process `p` or `p<n>`, owner as the process or `<process>.w<k>`, tag `<owner>.t<i>`. `run` checks that each tag exists, belongs to it and has the type of its pattern.
- `--owners` counts the owners of all processes and must be a multiple of `--processes`; each owner is a thread. "10 owners" is one process with 10 threads or 10 processes, and the performance test runs both. `scada-sim` starts no processes: each instance (`run --instance k`) is one simulator process with its owner threads, and the caller (a test, a person) starts one instance per process of the layout. That is how this decision reads "a configurable number of owner processes" of the issue; the review committee accepted it.
- A run stops on SIGTERM, SIGINT or SIGHUP, and by itself with code 1 once `scada-tagd` has been down for 5 s or the generation retires, so that an instance left behind by a test does not write on until it is killed. A shorter outage does not stop it (reference 3.3). SIGPIPE is blocked, so a closed standard output does not kill it. A parent-death signal is not used: it is a Linux `prctl`, and stopping children with their parent belongs in the test helper `ChildProcess`, not in each program.
- Patterns are functions of the tag index i and write count n, defined in `libs/scada-sim/README.md`: `check` (UINT64, the derivation the old test writer used, kept so that the fields stay derived from one another), `ramp`, `sine`, `step`, `walk` (FLOAT64, quality GOOD, no source time). `walk` takes steps from SplitMix64 of seed, i and n, so it needs no generator state per tag; it is not for security.
- `--rate` is the rate of the whole simulation, shared out by tag count so that every tag is written equally often. An owner thread writes, every 1 ms tick, what is due by then, at most 1,024 updates between two looks at the stop request, and calls `scada_tag_notify` after each such batch (or after every write with `--notify each`); `--rate 0` writes as fast as it can. The default rate is a tenth of the tags per second (reference 15.3). A run ends after `--rounds` or `--seconds`, or runs until SIGTERM; the process stays attached until the signal, so that the last values stay good. `--seconds` shares rate × seconds out among all owners by their tags, so no update is lost to rounding, and each owner writes its share evenly over the time.
- A simulator that attaches again to regions it wrote before goes on with each CHECK tag from the change count of its record, so that a reader still sees change count = write count (one exception after a kill mid-write, stated in `pattern.h`).
- `scada-sim` is a test tool, not part of the product image: it is installed only with the CMake install component `test-tools`, which a plain `cmake --install` leaves out (`cmake --install <build> --component test-tools --prefix <dir>`). No service unit. The test `install-layout` fails if it is in the staged tree.
- The rate test gates on the x86-64 pipeline machine, the one the acceptance of #18 names: all 500,000 updates written, at most 10 s + 100 ms, no update more than 250 ms late, and one process writing as fast as it can reaches 50,000 updates per second. On ARM64 the figures are reported only.
- The conformance tests 2, 3, 13 and 24 and the wake-up perf test use `scada-sim` as their writer; test 7 keeps the helper `scada-tag-test-peer`, which can leave a record in the middle of a write. `scada-sim` always calls notify, so the part of test 24 for a process that never notifies (the 100 ms cap) is not driven by it. `scada-tag-test-writer` is reduced to writing a tag from two threads, which contract 13.2 forbids and a simulator should not offer.
Reason (decided by the review committee of PR #59 for the install component and the rate gate): a naming rule needs no second parser of the tag-set file and makes a mismatch between file and run an error at start. Values from the write count make every value a reader sees checkable, which the integration test does exactly; a generator of `<random>` per tag would cost 2.5 kB for each of 50,000 tags. Per-tick pacing keeps the system calls at about 1,000 per second per owner at any rate; the batch limit keeps an owner that cannot keep up responsive to SIGTERM (before it, an overloaded run took tens of seconds to stop and stopped writing its heartbeat meanwhile). The reference does not list a simulator among the product components, so it stays out of the image. One writer for every load test keeps the derivation of `check` in one place.
Consequences: a tag set made for one layout cannot be run with another; `run` says which tag does not fit. Resolving and checking the tags takes about 0.5 s per 100,000 tags in a dev build and much longer under an emulator, so `run` writes its heartbeat every 256 tags while it does; without that, a large layout read as down while it started. The heartbeat period of a simulator process is 20 ms, so a heartbeat timeout below 60 ms (one third rule of contract 10.1) is not supported. On SCADA_E_RETIRING the simulator exits with code 1; following a generation change is issue P1-09. The rate is measured on the pipeline's x86-64 runner by `scada-sim-rate-perf-test` (pipeline step "Simulator rate"); on a 4-core development machine it gave 49,995 updates per second (the last update is written on the tick after it is due, 10,001 ms) with a worst lateness of 60 ms in both forms.

## D-42: Observer contexts: a read-only way into the tag database for tools such as scadactl
Date: 2026-11-15
Phase / issue: 1, #49 (first of the two pull requests of #19, P1-11)
Status: accepted; decided by the committee of the lead session on 2026-11-15, to which the owner delegated contract decisions; the read path reviewed and accepted by the committee on the owner's delegation on 2026-11-15 (review of #55), with the follow-ups below done in #55

Contract 0.6 had no way to do so: `scada_tag_attach` needs an entry in the process table with the caller's uid, and creates, locks and writes the process's regions, so a second instance got `SCADA_E_BUSY`. Nothing listed tags, owners or processes (`scada_proc_resolve` and `scada_proc_status` were named in section 13 but `scada_proc_status_t` was not defined, D-32). Coding standard 9 forbids reading the layout outside `libscada-tag`.
Options: A, an observer context in `libscada-tag` plus listing functions; B, `scadactl` as a configured process of the tag set (it would write shared memory, run one instance at a time and need one fixed uid); C, an inspection interface in C++ only, outside the contract (still a contract question, and `scada-api` will need the same listing in phase 4).
Decision: A (contract 0.9; the layout version stays 1, and no structure in shared memory, mode or file of `deploy/` changes), in two pull requests: this one (library, contract, tests) and the one of #19 (`scadactl`, C interface only).
- `scada_tag_observe` and `scada_tag_observe_opts` (which reuses `scada_attach_opts`; `retain_dir` is not used) make the checks of attach step 1 through the same functions, then read the tag directory and check the clocks. An observer has the process index `SCADA_NO_PROCESS` (0xFFFF), creates no file, calls no `flock`, opens nothing for writing, maps every region read-only through `PeerRegions`, and keeps no region descriptor. It keeps the base and generation directories open.
- In an observer context the write functions return `SCADA_E_NOT_OWNER` without a new branch: no owner is the observer's, so the existing ownership check answers. `scada_tag_heartbeat` and `scada_tag_notify` return `SCADA_E_INVALID` from a guard before they touch memory; they are the only functions that used the `proc` region of the caller unguarded. `scada_tag_notify` refuses rather than only refreshing, so that every call that writes for a process is refused alike, and `scada_tag_status` is the observer's one periodic call. `scada_queue_open` (P1-08, not built yet) is specified to return `SCADA_E_NOT_OWNER` in an observer context, so posting, acknowledging and `scada_waitset_add_queue` cannot be reached from one; reading queues from an observer is left to phase 10 (direct mode).
- `scada_tag_status` of an observer looks again for missing regions and repeats the clock check, as notify does for a process, and returns `SCADA_E_RETIRING` when the generation is RETIRING or when, at a look at most once a second, `current` names another generation (retiring is best effort, contract 11.3), the base directory under its path is another directory than at observe (the database set up again), or neither could be read at two looks in a row (`CURRENT_UNREADABLE_LOOKS`). The library does not swap the generation under the caller: the caller detaches, which unmaps everything, observes again and resolves its handles again; `scadactl tag watch` does that, and also calls status after every gap.
- `scada_owner_info` and `scada_tag_handle` list tags: `scada_status.owner_count`, then for each owner its `tag_count`, then `scada_tag_info` of `scada_tag_handle(owner, slot)`; a caller resolves a tag by name before it reads it. `scada_proc_resolve` maps a `proc` region and records that the process was asked for; `scada_proc_status` of a process never resolved in the context (other than the caller and `scada-tagd`) returns `SCADA_E_INVALID` with reason `SCADA_DOWN_NOT_RESOLVED`, so that a forgotten resolve is not a false "down", the trap #42 removed for tags; `scada_proc_status` (88 bytes, explicit reserved bytes) is real-time safe and reports state, the library's judgement of section 10.1 and its reason, the `down` flag of `scada-tagd`, heartbeat counter and age, `cycle_seq`, pid and uid. `scada_status.reserved1` became `owner_count` and `process_count`; the structure stays 32 bytes, checked by `static_assert`.

Reason: reference 18.2 and 11.6 expect `scadactl` to read shared memory itself, and reference 4.2 and 5.1 make read access a matter of group `scada`. Every member of that group can already open and map every `0640` region, so A widens nothing at the kernel level; it only lets such a reader go through the checks of the library instead of around them. `tag watch` needs no write: a futex wait works on a read-only mapping, and the owner wakes unconditionally (D-32).
Consequences:
- Who may observe is the file permissions: a member of group `scada`, or root. There is no registry of observers, and an observer's reads are not audited by the library. `scadactl` documents that membership of `scada` means unaudited read of every tag, and that it also allows creating files in `gen-<n>/` and taking the lock of a `proc` region, which can keep a process from attaching (an existing power of the group, not added here).
- Tests: the unit tests `Observer.*` and `TagHandle.*`; the integration test `scada-tag-observer-integration-test` (several observers beside a live writer and a live attach, only read-only mappings in `/proc/self/maps`, an observer before `scada-tagd`, a generation change); `scada-tag-observer-users-test`, with the new CTest label `root` and the test preset `root`, which becomes other users: root and a group member who is in no entry of the process table observe, a user outside the group gets `SCADA_E_PERMISSION`. The presets that run unprivileged leave the label out; the pipeline runs `sudo ctest --preset root` after the dev tests on both architectures. `Observer.ACallerWhoMayNotReadTheBaseDirectoryGetsPermission` takes the same path in both cases: as root it drops to nobody in a child, otherwise it removes the search permission of the base directory. The perf test `WakeLatency.EightWaitingObserversEachWakeWithinOneMillisecond` measures the wake of 8 observers on one ring against the target of P1-07.
- Accepted deviation (review of #55): RETIRING and `current` are looked at only in `scada_tag_status`, so calling it about once a second, detaching and observing again are the caller's duty (contract 11.4, items 5 and 6). The perf case with 8 observers reports only: its 99th percentile is noisy on shared machines.
- Open for phase 10, not changed now: (a) reference 11.6 gives direct mode to group `scada-emergency`, but the base directory is `2750 scada-tagd:scada`, so such a user cannot enter it; (b) the audit record of a `scadactl` invocation belongs in `scadactl`, not in the library.

Options, the size of the change: one pull request; the retain file and removal first, the queues in a RETIRING generation second.
Decision: A, a binary format with CRC-32, a new `scada_tag_retain_status`, and the split. This pull request: retained values and the removal of retired generations. Issue #65 takes the queues: posting refused in a RETIRING generation with the seq_cst handshake, requests answered ABORTED, cursors and ids in the new generation, undrained records counted at removal. It also takes the queue part of test 21.
- Format (contract 12, `src/retain_file.h`): header of 80 bytes with magic, version 1, record count, source generation and its `created_time_ns`, `written_time_ns`, flag FINAL, reserved, `config_hash`; records sorted by name, unique, each with type, name length, value and `source_time_ns`, padded to 8; a CRC-32 (IEEE, as zlib, our own table, checked against "123456789") over everything before it. The decoder checks every field and the exact length, and encodes back to the same bytes (fuzz target `retain_file_fuzz` with five seeds). Files of more than 64 MiB are refused; an owner whose file would be larger is reported as not persisted.
- Write: exactly `openat(".tmp.<owner>.bin.<pid>", O_WRONLY|O_CREAT|O_EXCL|O_NOFOLLOW|O_CLOEXEC, 0600)`, `fchmod 0640`, `write` in a loop, `fsync`, `renameat`, `fsync` of the directory; on any error unlink and, later, a fresh file; never a second `fsync` on one descriptor. The calls go through `RetainFileOps`, a seam for the power-loss model of the tests. The writer runs on a thread of its own (`RetainWriter`), so that an `fsync` stall does not stop the heartbeat of `proc.tagd` and the watchdog; the removal of files of owners that are gone and its directory `fsync` run there too. The liveness thread waits for the writer at most 5 s (`flush`, the stop), logs when the bound is hit and logs values left unsaved at exit. The writer's stop ends after the file in flight; files still waiting are not written; of several files of one owner waiting, only the newest is written; unchanged values are not written.
- Read: `O_NOFOLLOW|O_NONBLOCK`, `fstat`: a regular file, owner `scada-tagd`, `st_nlink` 1, at most 64 MiB; read, not mapped. A tag is taken from the owner's own file; a tag it lacks (moved to this owner) from the most recently written other file that has it with the same type; at most 1,023 other files, one at a time, keeping only the wanted values. No owner's file `<owner>.bin` can take the form `.tmp.<owner>.bin.<digits>` of a temporary file, since it ends in `.bin`, and no temporary file ends in `.bin`; in addition the tag-set builder refuses an owner name that starts with `.` (committee review), so no owner file starts with `.tmp.` either. The retain directory is opened with `O_NOFOLLOW` and checked for owner, mode and group (that of the base directory), by `scada-tagd` and by attach; an attach that finds it unusable restores nothing and counts it in `directory_unusable`. `st_nlink` 1 relies on `fs.protected_hardlinks` 1 (contract 3).
- What is persisted: the raw record read with the sequence lock of 6.2, without the owner-down overlay (through it every tag of an owner that left would be BAD with OWNER_DOWN). Quality GOOD or UNCERTAIN, not NOT_INIT, a valid BOOL, is a value. A record read consistently with quality BAD and without NOT_INIT removes the tag from the file at the next write (committee review: the owner wrote the tag and marked it bad, and a restart must not bring back an older value). A record with NOT_INIT says nothing about the value: the owner has not written the tag since its region was created, for example because its restore failed (an unusable retain directory, a rejected file), and removing it would destroy the persisted values within one interval (C++ re-check). It keeps the value on file, as does a record that cannot be read consistently (mid-write at all 64 attempts, an odd or changing `seq`) and any other record that is no value (an invalid BOOL). STRING tags cannot be retained: the tag-set builder refuses `retain` on them.
- Writes: a RETAIN_NOW change at the next check (every 50 to 250 ms); other changes at most once per `--retain-interval-ms` (default 5000, 100 to 3,600,000); the first write of an owner at once; all on SIGTERM (`flush_retained`). `scada-tagd` reads the `tags` regions of the current generation through `PeerRegions` with `look_now` at every check, so a region that has just appeared is read at once (once a second would break the 1 s of RETAIN_NOW).
- Left (committee condition): the owner's process stored a state other than RUNNING, or no longer holds the lock of its `proc` region (tested by taking it for a moment; a late attach that meets that lock in a RETIRING generation is told RETIRING, not BUSY). A stale heartbeat alone is not enough. Then `scada-tagd` reads the owner's RETAIN tags there, plus the tags the current generation retains, and writes its file marked FINAL with the identity of that generation (number and `created_time_ns`, since numbers restart at each boot). The mark stays on later writes. Nothing is written for an owner from an older generation once it has a ready `tags` region in a newer one, or once its file is marked FINAL for a newer generation; this also holds for a generation finished at start (committee review, blocking 1).
- Removal: once every owner's FINAL file is confirmed on disk by the writer (after the directory `fsync`) and no `proc` region is locked; or 30 s after it was retired, counted from the start of `scada-tagd` after a restart. Then the values of a process still attached are written, not marked FINAL, and the processes still holding their lock are logged with their pid. Unlink only, never truncate. A generation that cannot be removed is tried at every check for at most 60 s after it retired, then logged as abandoned and left to the next boot. At start, a generation without a live process is finished (its files written and waited for) before `clean_base_directory` removes it. A restarted `scada-tagd` finds retired generations by scanning, also when it reuses `current`, and sets one left RUNNING to RETIRING.
- Attach: before the region is published, waits at most 2 s, polling every 20 ms on CLOCK_MONOTONIC, until every owner that holds one of the new owner's retained tags in a RETIRING generation still present has its FINAL file for the newest such generation, or that directory is gone; on timeout it takes the files as they are and counts it. One deadline per attach, however many owners it waits for. A restored value is UNCERTAIN with RESTORED, its stored source time, and the restore time as update times; RESTORED lasts, with no time limit, until the owner writes the tag, and a reader tells a restored value by that flag alone (`age_ns` is the time since the restore).
- `scada_tag_retain_status(ctx, scada_retain_status_t*)`, 16 bytes: values restored, files rejected (at each look), waits that ran out, restores not done because the retain directory was unusable; since attach; zeros for an observer; not real-time. `scada-tagd` logs a rejected file once.
- Clean-up: once no generation is retired and every owner of `current` has its file, files of owners that are in no generation are removed. An owner with a value but no file of its own, or whose file holds a name it has nowhere, is written at the first check.
- Deployment: `tmpfiles.d/scada-tagd.conf` gets `d /var/lib/scada/retain 2750 scada-tagd scada -`, and the drop-in `scada-tagd.service.d/retain.conf` has `ReadWritePaths=/var/lib/scada/retain`. `StateDirectory=` would give the directory the service's group, not `scada`. The paths are those of reference 4.4, not those of a distribution. `scada-tagd` checks owner and mode and does not create the directory.
Reason: A needs no new mechanism in shared memory, and the FINAL file is on disk before the old directory goes, so the removal cannot race it. Option B would read a directory that may already be gone. A check sum and a strict decoder turn a torn or damaged file into "ignored", never into a wrong value. A writer thread keeps a slow storage device from making `scada-tagd` look dead. The split keeps each pull request reviewable.
Consequences:
- Tests: `RetainFile.*`, `Crc32.*` and `RetainDirectory.*` (format, every bit flip and every truncation, owner, link, second name, temporaries, precedence); `PowerLoss.*`, a model of the file system in which a crash at every step leaves either set of directory entries and, for unsynced data, nothing, a prefix, damaged bytes or all of it: the loader always finds the old or the new values; the model catches a writer without `fsync`; ENOSPC and EIO on create, chmod, write, fsync and rename keep the old file and leave no temporary; the call order is asserted. `Restore.*` and `RestoreAfterChange.*` (restore, reuse, damaged files, a moved tag, the wait ended by the FINAL file, bounded, a FINAL of another boot with the same number, no wait without a retiring owner, the C interface); ## D-46: `scada-tagd` reports broken and missing queues; no system suspend, and how a suspend is detected
Date: 2026-11-15
Phase / issue: 1, #53 (points 1 and 5, the first of its two pull requests; points 2 to 4, the base sequence of a recreated queue, are the second)
Status: accepted. Decided by the committee of the lead session (C++, SCADA architecture and Linux reviewers; the owner delegated these decisions to it) on 2026-11-15: the split of #53, the report (Q4, with the missing file and the unmapping), and suspend (Q5, option A with detection).

Context: a queue whose cursor and `write_seq` are out of range, or whose file was replaced inside the generation, is stopped (contract 9.2, D-40), but only its two ends see it. Issue #53 asks `scada-tagd` to apply the same range rule at each liveness check and report such a queue with its name, cursor, `write_seq` and capacity. It also asks what happens across a system suspend, during which `CLOCK_MONOTONIC` does not advance, so that a write request with an `expiry_mono_ns` set before it can be executed after the resume, later in real time than its requester allowed; contract 3.4 said nothing about it.
Options, the reads of `scada-tagd`, which is neither side while both may run: the cursor, then `write_seq` once; `write_seq`, then the cursor; `write_seq`, the cursor, `write_seq` again. Options, reporting: at every check; once per change of state. Options, suspend: forbid it as a deployment requirement (A); measure the lifetime of a write request on `CLOCK_BOOTTIME` (B).
Decision:
- At each check, after every `proc` region is observed, `GenerationHost::check` maps each queue region read-only (the checks of 3.1 and the identity the library uses; no descriptor kept, since a generation may have 4,096 queues; unmapped and mapped again when the name refers to another file or the file was shrunk, as `ProcProbe` does) and reads `write_seq`, the consumer's cursor and `write_seq` again, with acquire. The queue is broken if the cursor is beyond the second `write_seq` or the first is more than the capacity beyond the cursor (`queue_pair_broken`). The consumer never moves its cursor past `write_seq` and the producer never moves `write_seq` more than the capacity past the cursor, which only grows, so a pair in range at every moment is never found broken; either single read of `write_seq` can be (the tests give both cases as values). A queue whose region or consumer's `proc` region is missing, or whose consumer is not RUNNING, is not judged and keeps its last state: a `proc` region created anew holds cursor 0 from its rename until attach sets the cursors to `write_seq`, and a check in that window found a false "queue broken" (Linux reviewer, review of PR #68; `Queues.TagdJudgesNoQueueOfAConsumerThatIsNotRunning` fails without the rule).
- An events or command queue with no usable file at two checks in a row, while its producer was not down at either, is reported missing, once, and found again when the file is back (committee, Q4). A producer creates its queue files at attach, so a missing one was removed or damaged; one miss is not reported, because a check can fall between a removal and the rename of the new file. A producer that is down may not have created it yet. Result queues are left out as the committee worded it: they carry no command and no audit record.
- `CheckReport.queues` holds a `QueueChange` with a `QueueEvent`: BROKEN, NO_LONGER_BROKEN, MISSING, FOUND. `scada-tagd` logs `queue broken` at WARNING with `QUEUE`, `CURSOR`, `WRITE_SEQ`, `CAPACITY` and `REASON` (`replaced` for the all-ones cursor of D-40, otherwise `out of range`), `queue no longer broken` at NOTICE with the first four, `queue file missing` at WARNING and `queue file found again` at NOTICE with `QUEUE`. Once per change, so a queue that stays broken until the next generation does not fill the log. Alarms follow in phase 2. The library does not use the result.
- Suspend, option A (committee): contract 3.4 requires that the unit does not suspend, hibernate or hybrid-sleep, and `CLOCK_MONOTONIC` stays the clock of every `*_mono_ns`. The platform disables them; `docs/install.md` gives the lines (mask the sleep targets of the service manager, `AllowSuspend=no` and the other `Allow*` settings of its sleep configuration). Masking cannot be checked from inside a unit, so `scada-tagd` detects the traces: at start it logs once at INFO the sleep states `/sys/power/state` lists (at WARNING it would fire on every normal unit, since most kernels offer them with the targets masked, and carry no information: lead session, review of PR #68); at start and in every round of its main loop it samples `CLOCK_MONOTONIC`, `CLOCK_BOOTTIME` and `CLOCK_MONOTONIC` again (`SuspendWatch`), and logs a WARNING when the time spent suspended since boot is above 0 at start (`the system was suspended since boot`) or grows (`the system was suspended`), with `SUSPENDED_MS`, rounded up so that a suspend under 1 ms does not read as 0. Only what lies beyond the reading interval counts: the difference lies between `boottime - monotonic_after` and `boottime - monotonic_before`, so a slow read never counts as a suspend. A paused virtual machine stops both clocks and is invisible to both checks; contract 3.4 says so. `scada-tagd` reports a suspend and does not act on it.
- Not in this decision: retiring the generation on a detected suspend, so that pending requests are answered ABORTED (the Linux reviewer's proposal). It is restart behaviour and builds on the generation change of P1-09; it is an open point of contract 16, to be put to the committee once that is on `main`. The proposal's sentence "a unit that resumed is treated as restarted" is dropped until then, since nothing checkable stands behind it.
Reason: the three reads are the cheapest order that gives no false report, and a false "queue broken" would send people after a fault that is not there. A controller that sleeps is not controlling. Option B would fix only the request lifetime: heartbeats, ring and queue waits (futex timeouts take only `CLOCK_MONOTONIC` or `CLOCK_REALTIME`) would stay on the monotonic clock and see every process fresh after a resume; one clock for every age and timeout keeps the rules of sections 9 and 10.1 as they are.
Consequences:
- Contract 0.13: sections 3.3 (the `SIGBUS` risk of the queue mappings of `scada-tagd`), 3.4, 9.2, 16 and 17 (item 20); the layout version stays 1.
- `libscada-tagd` gains `scada/tagd/suspend.h` (`SuspendWatch`, `sample_clocks`, `read_sleep_states`). `/sys/power/state` is a Linux kernel interface, not a path of a distribution.
- Tests: `Queues.TagdReportsAQueueWhoseCursorIsOutOfRange` (reported once, and its repair), `TagdReportsAWriteSeqTooFarAhead`, `TagdReportsAReplacedQueueAsBroken`, `TagdReportsNoQueueThatIsMissingOrInRange`, `TagdReportsAQueueFileMissingForMoreThanOneCheck`, `TagdReportsNoMissingFileOfAProducerThatIsDownOrOfAResultQueue`, `TagdReportsNoMissingFileAcrossAFastRestartOfTheProducer` (old heartbeat still fresh), `TagdJudgesNoQueueOfAConsumerThatIsNotRunning`, `TagdReportsNoBrokenQueueWhileBothSidesRun` (20,000 records through a queue of 4 places with the check in a loop and both heartbeats written in it, since a ThreadSanitizer run outlasts the heartbeat timeout; it shows the reads of the running code, not a wrong order, whose window is too short to hit), and `QueuePairBroken.*`, which give the interleavings as values and fail for either single read. `SuspendWatch.*` with injected clock samples (no suspend whatever the read time, a suspend before the start reported once, a suspend while running with its length, a clock that goes back), and `SleepStates.*` (trimmed, empty or missing, outside input).
- A queue that is broken stays broken until the next generation (D-40) until the second pull request of #53.

## D-47: Late heartbeats and restarts in the log: MESSAGE_IDs, a rate limit, a count of lives in `ProcHeader`
Date: 2026-11-15
Phase / issue: 1, #61
Status: accepted. Points 1 and 3 were decided by a committee of a C++, a SCADA architecture and a Linux systems reviewer on the owner's delegation, unanimously, on 2026-11-15; the other points are the simplest choice that fits the documents.

Context: D-36 and the review of pull request #48 left six points. A late heartbeat is only a WARNING in the log, while reference 14.4 expects a system alarm for service faults; neither the alarm service nor the journal exists in phase 1 (reference 10.3, 10.4, 18.2). The record is logged once per process and check, so persistent overload with a short check interval could reach journald's rate limit and drop other records. A process that restarts into its reused `proc` region between two checks is never seen down by `scada-tagd`. `LAST_LATE_MONO_NS` is in ns while journald's monotonic stamps are in µs. The several-threads heartbeat test passes with the old writer on one CPU. The compare-and-swap loops of the heartbeat have no `cpu_relax()`.
Options, point 1: a documented hook in the system log; an `events.tagd` reliable queue (no consumer exists, so it fills; "no audit, no action" semantics); system tags owned by `scada-tagd` (the tag-set builder has none yet; better with `scada_proc_status`, #49). Options, point 3: a count in reserved bytes of `ProcHeader`; comparing `ProcHeader.pid` between checks (the contract forbids decisions on the pid, and reuse of a pid or two restarts give a wrong answer); systemd's restart count only (`NRestarts` counts only automatic restarts, resets when a unit is stopped and started, and does not see manual starts, tests or `scada-sim`).
Decision:
- Point 1: every liveness record of `scada-tagd` carries a fixed journald `MESSAGE_ID`, written as its last field: `process down` `51ad850aac4848fab6eade0000eaa868`, `process up` `3e293a9e793b4fa08fafb02b5f16ae7f`, `heartbeat late` `31aad0d613b645d39a83e7978c4531ec`, `heartbeat late before this check` `c4de2438d3574ca38f45771de9254e3a`, `process restarted` `f35dfeb8e8124cc88b219cabf6947b00`. The IDs and the fields are listed in `libs/scada-tagd/README.md`. They are a provisional diagnostic input for the alarm service, not an authority: any local process can write a journal record with the same fields. The natural input of the alarm service is `scada_proc_status` or system tags, not parsing the log; the name of the alarm is left to its phase (reference 10.4 lists "service down"). When the journal datagram fails, the record goes to the standard error stream as one line: the ID and the fields are then text in the message, not journal fields.
- Point 2: at most one `heartbeat late` per process in 10 s (`LATE_LOG_INTERVAL_NS`). The first growth is logged at once; growth within the 10 s after a record is summed into `LATE_BEATS` of the next one, logged at the first check after the 10 s, and `CHECKS` says how many checks it sums. What is held is logged when `scada-tagd` stops. A baseline is logged at once and starts no interval. `process down`, `process up` and `process restarted` are never held. At most 4 records per process in 30 s keep a full process table (1,024) below journald's default of 10,000 in 30 s per unit; the unit template sets no `LogRateLimit*`, and journald drops beyond its limit while the sender sees success. `LATE_BEATS_TOTAL` lets a reader see records that were lost.
- Point 3: `ProcHeader` takes `starts` (u32, offset 48) from its reserved bytes; 12 stay reserved (offset 52); size 64 and layout version 1 are unchanged and asserted. Attach increments it (relaxed) at step 6, just before RUNNING, whose release store publishes it: it counts lives that reached RUNNING, and a failed attach counts nothing. Never reset within a region; a new region or generation starts at 0, and `scada-tagd` takes a new baseline. `scada-tagd` counts its own lives too but does not watch them. At every check at which a process is up, `scada-tagd` loads `state` with acquire, and only if it is RUNNING loads `starts`; the first sample of a mapping is a baseline. Growth n is logged as `process restarted` with `RESTARTS` n, `RESTARTS_UNSEEN` n minus the checks since the previous sample that found the process up after it was down (at least 0; a check that found it up but could not sample, because it left RUNNING in between, keeps its credit), and `STARTS_TOTAL`; WARNING with an unseen life, NOTICE without. A life of a library before 0.14 leaves the count unchanged: a lower bound. Diagnosis only: never used to judge liveness and never a second restart limiter; systemd's limit stays the only one (reference 4.2, D-22).
- Point 4: the log field is `LAST_LATE_MONO_US`, in µs (truncated), the unit of journald's monotonic stamps, so that it can be compared with `__MONOTONIC_TIMESTAMP` of the same boot. The shared-memory field `last_late_mono_ns` stays in ns. `LONGEST_GAP_MS` stays in ms. One unit per field, named in it.
- Point 5: said, not changed. The lost-count part of `LateHeartbeat.HeartbeatsFromSeveralThreadsLoseNoCountAndNeverGoBack` needs two CPUs to fail with the old writer; the pipeline's runners have four. The other part, a time not newer is never published, is tested on one thread by `LateHeartbeat.ATimeThatIsNotNewerIsNeitherPublishedNorCounted`, which fails with the old writer on any number of CPUs. Making the count part independent of the CPUs needs a hook inside a real-time function or a model of the loop; neither is worth it for a `fetch_add`. The test says so in a comment.
- Point 6: no `cpu_relax()` in the compare-and-swap loops. Coding standard section 11 asks for it in a short retry loop that waits for a writer in another process (the sequence-lock read). A failed compare-and-swap returns the newer value, and the next attempt uses it at once; the loops do not wait for anything, and they retry only when another thread of the same process published meanwhile.
Reason: the log hook gives the later alarm service a stable key at no cost to the interfaces; the queue and the tags each need an interface that is not built yet. Only the owner of a region sees every life, as it sees every gap (D-36); the pid cannot count and systemd does not see every start.
Consequences:
- Contract 0.14, sections 10 and 10.1, with a migration note. Review by a person: shared-memory layout.
- `libs/scada-tagd/src/late_log.{h,cpp}` (the rate limit) and `report_log.{h,cpp}` (the records) leave `tagd.cpp`.
- Tests that fail without the change: `LateLog.*` and `ReportLog.*` in `scada-tagd-unit-test` (a datagram socket stands in for the journal and each record kind is checked for its ID and fields; the sum of the rate limit), `Host.ARestartBetweenTwoChecksIsReported`, `SeveralRestartsBetweenTwoChecksAreCounted`, `ARestartSeenAsDownAndUpIsNotUnseen`, `LivesFoundAtStartAreABaseline`, `ALifeThatDoesNotCountItselfIsNotReported`, `LateHeartbeat.StartsCountsLivesAndIsReadOnlyWhileRunning`, `Conformance01Layout.ProcHeader`.
- `scada_proc_status` and `scadactl status` should show `starts` and the late-beat figures (issue #49).
- D-36: its follow-ups "a system alarm or journal record" and "a count of fast restarts" are done here, the alarm itself waits for the alarm service.

## D-48: Test processes die with the test binary; a cleaner process removes the temporary directory of a killed test
Date: 2026-11-15
Phase / issue: 1, #64
Status: proposed

Context: `ChildProcess` stopped its child only in its destructor, so a test binary killed by SIGKILL, a CTest timeout or a cancelled job left `scada-tagd`, the peers and an unbounded `scada-sim run` running, and its `/tmp/scada-tag-it-*` directory (32 MB) behind. D-41 put stopping children with their parent into the test helper, not into each program. The issue leaves open how, what happens to the directory, and whether CTest's timeout already kills grandchildren. CLAUDE.md forbids architecture-specific and distribution-specific code outside the I/O HAL.
Options, children: a parent-death signal set in the child between fork and exec (`prctl(PR_SET_PDEATHSIG)`); a process group or session per test killed by a watcher; a watcher process that kills registered pids; a parent-death signal in the programs (rejected by D-41). Options, directory: leave it and sweep stale directories at the next start; a cleaner process that removes it when the test process ends; a directory that the kernel removes (none in POSIX).
Decision:
- `ChildProcess::start` forks and execs itself instead of calling `posix_spawnp`, which has no hook between fork and exec. The child sets `PR_SET_PDEATHSIG` to SIGKILL, then compares `getppid()` with the parent's pid taken before the fork and exits without exec if they differ (the parent died before the signal was set). Everything the child needs (the program path, found on PATH as `execvp` would, and the argument vector) is prepared before the fork, so the child makes only async-signal-safe calls. A byte in a close-on-exec pipe reports a failed exec, so `start` still returns nothing for a program that cannot be started. The interface of `ChildProcess` is unchanged except for the new `pid()`.
- `scada::test::TempDirectory` makes the temporary directory of the fixtures `TagProcesses` and `TagdService`. It starts `scada-test-cleaner <dir>` with a double fork, so the cleaner's parent becomes the reaper of the system, and `setsid`, so a signal to the test's process group does not reach it. The cleaner's standard input is a socket from the test process: a byte means the test removed the directory itself (the normal teardown removes it first, then sends the byte, then waits for the cleaner's end); end of file without a byte means the test process is gone, and the cleaner removes the directory, trying again at most 500 times 10 ms apart while children that got SIGKILL have not yet ended.
- `prctl` and `pidfd_open` are Linux calls in test-only code. They are operating-system specific, not architecture specific, and no distribution path or tool is used (`/dev/null` and PATH lookup only); the test helpers were already Linux only (`pidfd_open`, `ptrace`). Nothing changes in the product binaries.
Reason: a parent-death signal is the only one of the options that covers SIGKILL of the test without a further process per child, and it needs nothing from the programs. A sweep at the next start leaves the directory until some later run, and never on a machine that does not run the tests again. CTest 3.28 was checked by hand: on a timeout it kills the test and its descendants, also those in a session of their own, but not a process that has already been reparented to the reaper; so the timeout alone already stops the children, while a SIGKILL of the test binary alone (a person, a cancelled job, the OOM killer) did not, and a cleaner must leave the process tree to survive the timeout.
Consequences:
- The parent-death signal fires when the thread that started the child ends, not only the process: a child must be started from a thread that outlives it, which `child_process.h` and `tests/README.md` state. Checked at every place a `ChildProcess` is started (review of #71): all run on the main thread of the test; the two `std::jthread` sites (tag access readers, wake-up perf) only read, no test uses a death test or `std::async`, and the `fork` in the scadactl test execs `scadactl` itself. The child between fork and exec makes only async-signal-safe calls (`prctl`, `getppid`, `open`, `dup2`, `execve`, `write`, `_exit`); keep it so.
- Not covered: a process a child starts itself (none of the programs does; `env` and the emulator exec in place); a set-user-ID program, or a child that changes its credentials, which clears the signal; the children forked by `observer_root_integration_test.cpp` and the traced program of `trace_marked_syscalls` (bounded by its `alarm`), which do not use `ChildProcess`; the temporary directories of the unit tests, which start no processes.
- The cleaner itself is gone once it has removed the directory, or after about 5 s if it could not.
- `kill()` and `stops_cleanly()` of `tagd_fixture.h` treat a child that has already ended as gone and judge it by how it ended (`ChildProcess::wait_for_ending`): `kill()` returns the ending and writes a note when it was not SIGKILL; `stops_cleanly()` still needs exit code 0. Found in `Scadactl.TagWatchNeverShowsTheTagsOfARetiredGeneration` (flaky under `ctest -j8`): its `scada-sim` writer exits by itself with code 1 once the second `scada-tagd` retires generation 1 (D-41), so under load it was often reaped before the test reached `kill()`, and `send_signal` returned false. The early exit is the designed one; the test now expects that exit, with its reason on the standard error stream, instead of killing the writer.
- Test: `scada-test-cleanup-integration-test` starts `scada-test-killed-runner`, a test binary with the fixture `TagProcesses` that starts `scada-tagd` and two `scada-sim run` processes, kills it with SIGKILL, and expects the three processes and the cleaner to end and the directory to be gone. Without the parent-death signal the test fails with the processes still running; without the removal it fails with the directory left.

## D-49: Base sequence of a queue file created anew inside a generation; the consumer follows the file
Date: 2026-11-16
Phase / issue: 1, #53 (points 2 to 4, first of their two pull requests; the second is D-51)
Status: accepted. Option A of the design (issue #53) was decided by the committee of the lead session (C++, SCADA architecture and Linux reviewers; the owner delegated these decisions to it) on 2026-11-15, with conditions C1 to C14. The split was accepted on 2026-11-15. Q2 was accepted as reworded by the committee. The three questions the C++ reviewer could not verify were answered in issue #53 before the build.

Context: a queue file that is removed, shrunk or damaged and created anew by its producer inside a generation stayed dead until the next generation (D-40). Two gaps stayed open. (a) Posts between the recreation and the consumer's next look returned `SCADA_OK` and were lost; on an events queue that is an action without an audit record. (b) A consumer that was not attached could not tell the new file from the old one, and ids could repeat. The committee rejected two simpler fixes: the consumer goes on using the unlinked file for up to 1 s, and records delivered but not acknowledged share ids with new ones.
Options: A, a base sequence in `QueueHeader` from the producer's high-water mark and the consumer's cursor; B, from the cursor alone; C, a creation stamp.
Decision: A.
- Layout (C6): `QueueHeader.base_seq` (offset 16), `flags` (offset 24, bit `QUEUE_BASE_SET`) and `reserved0` (offset 28) come from the reserved bytes; 32 stay reserved; size 64; layout version 1. LayoutChecks and the lock-free test cover the fields.
- Producer: the cursor slot of a queue in its own `proc` region holds the high-water mark H. `post_record` stores `H = w + 1`, relaxed, after every refusal check and before `store_record` (C4); a crash in between burns the id. A queue with one process at both ends ends the process before the slot is used (C5). When `attach_queue` creates the file, it sets the base `B = max(H', R')` and `write_seq = B` before `ready`:
  - H' is the mark if the `proc` region was reused;
  - R' is the consumer's cursor plus the capacity, if the cursor is readable, not 0 and not all-ones;
  - H > R' is impossible and is ignored as damage;
  - without room for a capacity of ids (2^48 for CMD), the file is created dead: `QUEUE_BASE_SET` with base and `write_seq` all-ones, which a consumer refuses and by which the producer gets `SCADA_E_PEER_DOWN` (as the design said; the first version gave an older-style file at 0, review of PR #77, N3).
  The producer removes its own unusable file before it creates one, because the rename that publishes a region does not replace (C11). Contract 9.1.
- Consumer (`Attachment::follow_queue`, before each look and at attach):
  - It uses the first file it sees. A cursor below the base always jumps to the base; positions below it are in no file it can reach (C3).
  - It keeps the file in use while the name is missing or a different file fails the checks (Q2 as reworded: ENOENT or an invalid other inode).
  - On a different valid file it reads the old `write_seq` again (C2), delivers up to it, then jumps and counts `skipped` and `replaced`.
  - The `QueueHeader` of every file is outside input (`queue_base_of`): a flag bit other than `QUEUE_BASE_SET`, `reserved0` not 0, or a base that is all-ones or beyond `write_seq` make the file refused, not ignored (review of PR #77, B5).
  - Two mappings of the same device and inode are the same file: a file mapped again after a look that failed is the file in use (B2; the first version told files apart by mapping address, and a rename away for one look killed the queue).
  - It stops the queue and stores the all-ones cursor when:
    - the new file has no base (older build, D-40), or a header that is refused;
    - its base is below the old `write_seq` (C2);
    - the file in use changed size in place: each `PeerMapping` has a `whole` flag, which a look (in `scada_tag_notify` or a wait, never in real-time code) clears by name for the current file and by `fstat` on the descriptor now kept for each older queue mapping, before it publishes a newer one. So a file shrunk and then replaced is not read, and `scada_queue_next` takes no lock and makes no system call for it (B3, B6: the first version called `fstat` under the peers' mutex on every look while an old file drained, and read a `resized` count after the mapping);
    - the name reached the 16-mapping limit (Q2, `PeerRegions::at_mapping_limit`).
  - `scada_queue_ack` returns `SCADA_E_INVALID` and stores nothing when the cursor is no longer at the delivered record (C1): the cursor never moves back except to all-ones.
  - For a new `proc` region, `start_cursors` counts as skipped only what lies between the base and `write_seq`.
- `scada-tagd` (C13): it remembers each queue's file, `write_seq` and the consumer's cursor at its last check, across a missing name. When another file appears it reports `QueueEvent::RECREATED` and logs at WARNING `queue file created anew; audit records may be lost` (events) or `...; records may be lost`, with `QUEUE`, `BASE_SEQ`, `OLD_WRITE_SEQ`, `CURSOR` (at the last check of the old file), `LOST_AT_MOST`, `LOST_IDS` as `[from, until)` and `MESSAGE_ID` `330f9ce1bb0547c098562d406ce2f774` (N1). The range (`lost_ids`) runs from that cursor to the new base, a true upper bound, since every id of the old file is below the base. Without a base the bound is `unknown` and the range `[from, ?)`. It is never inverted. The first version took the cursor at report time and the old `write_seq` of the last check, which gave `[5, 3)` and 0 for four lost audit records (review of PR #77, B1). `scada_queue_stats` is per process and lost at a restart; the system log is not. A `scada-tagd` that did not see the old file (it was restarted) cannot report it; the consumer still counts the skip.
- Residuals, in contract 3.3 (C10 and the three answers in #53):
  - ids can repeat for a consumer that was not attached when the queue file and the producer's `proc` region are lost together with the consumer's cursor at 0, or when all three regions are lost; that is likelier than it reads, since cleanup by name removes a process's files together;
  - the `proc` lock is an `flock` on one file, so two producer instances can live if a running process's `proc` file is removed;
  - a shrink of an already unlinked file cannot be seen by name;
  - kept mappings count against the locked-memory limit, up to 16 times the queue's size.
- C14: the library keeps no acknowledgement latch. Whether commands stay refused after lost audit records until an operator acknowledges is unspecified and safety-relevant; it is an open point of contract 16 for the owner, before the command service (phase 5). Follow-up issues, without the phase-1 label: #74 (a loss record in the audit chain, reference 13.4), #75 (a system alarm for lost audit records and a broken queue; reference 10.4 has none), #76 (`scadactl status` shows queue state). Contract 17, item 22, lists the differences from reference 5.3 and 18.2.
Reason: both bounds hold under concurrency without a lock. Every id is below the cursor at its post plus the capacity, and the cursor only grows. The mark is the exact next position whenever the producer's region survived. Delivering the old file first closes gap (a) when the consumer holds it. The jump only moves forward, so no id repeats in the cases above. An older build reads the new fields as invalid records or a dead queue, never as a repeated id, so layout version 1 stays.
Consequences:
- Contract 0.15: sections 3.3, 9, 9.1, 9.2, 9.3, 10, 13 (`skipped`, `replaced`), 15 (conformance test 29), 16, 17 (item 22), change log and migration note. `docs/install.md`: limits for kept descriptors and mappings (N4). Issues #74 and #76 are labelled phase 4, #75 phase 7 (N6).
- Left for D-51 (#53, second pull request, which closes it):
  - the periodic look while a consumer waits in `scada_queue_next` or a wait set (Q3), with try-lock in `scada_tag_notify`;
  - `scada-tagd` reporting a `write_seq` that falls (C10);
  - the stress cases truncate in place and the 16th file.
  Until then a consumer that never calls `scada_tag_notify` moves to a new file only when its own region is missing, as before. 2a stops the queue in every case 2b handles in more detail (same-inode shrink, the mapping limit), as main did.

## D-50: Tests that depended on machine speed under load: a held simulator, a long heartbeat timeout for the load tests, a feeder that stamps again
Date: 2026-11-16
Phase / issue: 1, #62
Status: accepted. Decided by the committee of the lead session (the owner delegated these decisions to it) on 2026-11-16: option A for the start of the simulator, the 30 s timeout, the bounded re-stamp of the feeder, and leaving the contract's time bounds.

Context: `scada-tag-access-integration-test` and `scada-tag-rt-integration-test` failed now and then under load. Runs on `main` (4 cores, a busy loop on every core, `ctest -j8` in a loop and 4 to 8 test binaries in parallel; 976 runs of the access test, 400 of the rt test) found four causes, none a defect in the library:
1. In `run_load` the simulator starts writing right after it attaches, while the test still resolves 50,000 names and starts its readers. A simulator that wrote its 40 rounds first (928 ms in a captured case) printed `done` before any reader had read; the readers stopped with `reads=0`, and the test failed with "a reader did not read every tag once" (the sighting of PR #48). With the test at nice 19 and the simulator at nice -20 it failed 3 times in 3.
2. The load tag set had the default heartbeat timeout of 3,000 ms. On an overloaded machine (load average 18 to 40) the simulator's heartbeat was 3,373 ms late once (`scada-tagd` logged its own 3,556 ms), and readers were preempted for 3.2 s and 4.4 s inside one `scada_tag_read_many`, which reads the clock once (D-34). Both make a running owner read as down, as the contract says they should; the test counted them as faults (23 failures).
3. The feeder of the rt test stamped a request to expire 1 ms after its own clock read. The library refuses a request that has expired when it is posted (contract 9.4); more than 1 ms between the stamp and the post made the feeder give up, and the probe waited 30 s for a request that never came: 5 failures in 200 loaded runs.
4. The 2,000 ms limit of `Conformance05A*` and the 95 % rate of `Conformance02*` failed under the heaviest load only (7 and 2 failures). They are the contract's bounds.
Options for 1: (A) `scada-sim run --hold`, which waits after resolving for SIGUSR1; (B) a simulator without `--rounds`, stopped by SIGTERM once the readers have read while it wrote, which loses the check that every tag holds write 40 and the time of the maximum rate; (C) repeating a run in which readers and writer did not overlap, which is flaky by design. A wait in the test alone cannot do it: a reader that resolves before the simulator attaches finds its regions missing until the library looks again (at most once a second), and nothing in the test can hold the simulator between its attach and its first write.
Decision:
- (A). `scada-sim run --hold` prints `ready` after attaching and resolving and starts writing on SIGUSR1; SIGTERM, SIGINT and SIGHUP stop it while held (`stopped updates=0 elapsed_ms=0`, exit 0). It writes its heartbeat while held, and the rule for a simulator left behind (D-41: exit 1 once `scada-tagd` has been down for 5 s) applies while held, so a simulator whose test died does not wait for ever. `--hold` is the first option of scada-sim without a value. scada-sim is a test tool in its own install component, not a product interface.
- `run_load` starts the simulator with `--hold`, waits until each reader has read every tag once, releases it, and stops the readers only once the simulator is done and each reader has read every tag in a pass that began after the release. Each wait is on a condition with WAIT_LIMIT. "A reader did not read every tag once" now counts the passes after the release. A failure prints each reader's reads, busy reads and passes.
- The load tag set uses a heartbeat timeout of 30 s (`LOAD_HEARTBEAT_TIMEOUT_MS`, equal to WAIT_LIMIT), as the small tag set already gives `io` a long timeout so that a busy machine does not make it look dead. No check is removed: a reader still must never see the running simulator down. `SimProcesses.AnOverloadedRunStopsPromptly` keeps the default 3,000 ms under load, and the unit tests of the race (`TagAccess.Conformance03A*`, `Conformance23A*`) keep it too.
- The feeder stamps the request again when the post is refused with `SCADA_E_INVALID` and its own clock shows the 1 ms lifetime has passed, at most 1,000 times, and fails with "the request expired before the post <n> times" after that; any other refusal fails at once. The lifetime stays 1 ms, so the probe still finds the request expired before it looks and the library's EXPIRED answer is still traced. A longer fixed lifetime can be missed by a long enough stall; this cannot.
- (4) stays: the bounds are the contract's. `tests/README.md`, "Load", records the load the integration tests assume.
Reason: each fix removes a dependence on the speed of the machine without taking away a check, and the rule of D-34 is the contract's, not the test's to change.
Consequences:
- `scada-sim` gains `--hold` (help text, `services/scada-sim/README.md`, `libs/scada-sim/README.md`). Tests: `SimOptions.HoldIsAFlagOfRun`, `SimProcesses.AHeldSimulatorWritesOnlyAfterSigusr1` (several heartbeats and no tag written while held, every tag written after the release), `AHeldSimulatorStopsOnASignal`, `AHeldSimulatorStopsWhenTagdStaysDown`.
- The note of D-34 says that a reader preempted inside one `scada_tag_read_many` can see a running owner down.
- Tests that failed only under eight more test binaries in parallel on 4 cores are tracked in the issue "Tests that fail under extreme overload", not here.

## D-51: Queue consumers look while they wait; notify does not wait for a look; a kept mapping is used again; a falling write_seq is reported
Date: 2026-11-16
Phase / issue: 1, #53 (the second of the two pull requests of points 2 to 4; it closes #53)
Status: accepted. Q3, Q4 (the falling `write_seq`) and the split were decided by the committee of the lead session (C++, SCADA architecture and Linux reviewers; the owner delegated these decisions to it) on 2026-11-15. The bound for a shrink of an unlinked file and the reuse of a kept mapping were asked for in the review of PR #77. The wait-set readiness of a first file and of a file changed in size was asked for in the review of PR #86 (B1, B2, N1 to N4).

Context: after D-49 a consumer moves to a queue file created anew only at a look at its peers' regions, and looks happened only in `scada_tag_notify`, `scada_tag_status`, and in waits while a region was missing. A consumer that only waits in `scada_queue_next` or a wait set and never calls notify kept its old file. Then gap (a) of PR #56 stayed open longer than 1 s, as `SCADA_E_FULL` for the producer, and a file shrunk in place was not seen. `scada_tag_notify` is called from real-time loops, and its look took the peers' mutex, which a consumer holds while it maps and prefaults a region. Each look that mapped the same file again, after a failed `fstatat` for example, spent one of the 16 mappings of a name. And `scada-tagd` did not report a `write_seq` that falls, which only damage or a second producer can cause (contract 3.3).
Options, the look while waiting: in every wait slice (the per-region interval of 1 s bounds it); only while a region is missing (as before). Options, notify: wait for the lock; try the lock and skip. Options, a pending file in a wait set: the wait set follows it; the wait set reports the queue ready and the consumer's next look follows it.
Decision:
- `scada_queue_next` and `WaitSet::wait` call `refresh_peers` before each wait slice, also while every source is mapped; the descriptor thread of a wait set does the same. `PeerRegions::refresh` looks at a region at most once a second, so a waiting consumer costs one `fstatat` per region and second. A call with timeout 0 returns before the wait and makes no system call (conformance test 22 unchanged).
- A wait set does not move a cursor: its descriptor thread is not the consumer's thread. `Attachment::queue_switch_pending` is true while the consumer's next look changes the file in use: a first file is mapped while none is in use (review of PR #86, B1), another file is under the name, or a look found the file in use changed in size (B2). `Queue::ready` returns true for it, and the wait set's view of a queue (`WaitSetSeen::switch_pending`) includes it, so its descriptor is signalled. The consumer's next `scada_queue_next` then adopts the file, follows it or stops the queue (D-49); a queue stopped this way returns `SCADA_E_LAYOUT`, at once with timeout 0, and is not ready afterwards, so a wait set does not spin on it. Options for B2 were "not ready" and "ready once"; ready once was chosen, since otherwise a consumer that calls next only after a wake never learns of the stop.
- No thread reads a file a look found changed in size, nor the file of a dead queue: `Attachment::queue_bytes` returns an empty span for both (B2), which covers `Queue::ready`, `Queue::waiter`, and the wait set's `look_at` and `watched_word`. The pointer to the file in use is stored with release and loaded with acquire, since wait-set threads read the mapping it names (N1).
- `scada_queue_next` looks again at once, without the wait of a slice, when the look before the wait finds a switch pending; once per slice, so a switch that cannot happen yet does not spin (N2).
- `scada_tag_notify` calls `PeerRegions::try_refresh`, which returns at once while another thread holds the lock: that thread's look covers the regions, and the next notify looks. `scada_tag_status` and the waits still wait for the lock.
- A look that finds, under the name, a file it mapped before (same device and inode, the right size, still whole) publishes that kept mapping again and spends no mapping slot.
- `scada-tagd` reports `QueueEvent::WRITE_SEQ_FELL` when a queue's `write_seq` is below the value of its previous check in the same file. It logs `queue write_seq fell; ids may repeat` at ERROR, with `QUEUE`, `OLD_WRITE_SEQ`, `WRITE_SEQ` and MESSAGE_ID `d673f795274a49d1882153ae03003b15` (C10).
- Contract 3.3: a shrink of an unlinked queue file is seen at the next look, at most about 1 s later. A consumer that reads it before that look, or one that only polls with timeout 0 and never notifies, can be stopped by `SIGBUS`. A consumer blocked in next or a wait set reads `write_seq` at every slice (at most 100 ms) and the look runs at most once a second, so it usually meets `SIGBUS` before the look (N3).
- A kept mapping used again skips the header checks of section 3.1 of a fresh open; the range rule and the base stop a queue whose file was shrunk and grown again between two looks (comment in `PeerRegions::look`, N4).
Reason: the per-region interval already bounds the cost, so a look in every slice adds no rate limit of its own. Skipping the look in notify keeps a real-time loop from waiting behind a mapping and prefault; nothing is lost, since the thread that holds the lock looks. Only the consumer's thread may move its cursor (D-40), so a wait set only reports readiness.
Consequences:
- Contract 0.16: sections 3.3, 9.2 and 16; the layout version stays 1.
- Tests:
  - `Queues.AWaitingNextFindsAFileCreatedAnewWithoutNotify`, which fails without the look in the wait (checked), and `AWaitSetFindsAFileCreatedAnewWithoutNotify`. Both use a fresh context: the fixture's `look_again` sets the next real look of a region seconds ahead.
  - `NotifyDoesNotWaitForALookOfAnotherThread`, which holds the peers' lock through `PeerRegionsTestAccess`; notify would never return without the try-lock.
  - `TheSameFileMappedAgainSpendsNoMapping`: 17 renames away and back, no limit reached.
  - `TagdReportsAWriteSeqThatFalls` and `ReportLog.AWriteSeqThatFellIsAnError`.
  - `Queues.AWaitSetFindsAFirstFileCreatedAfterTheOpen` and `TheDescriptorOfAWaitSetFindsAFirstFileCreatedAfterTheOpen` (B1): both fail without the fix (checked; the wait times out). ## D-54: Queues in a RETIRING generation: posts refused, a seq_cst handshake, drains that answer ABORTED
Date: 2026-11-16
Phase / issue: 1, #65 (P1-09b, the second pull request of P1-09)
Status: accepted; the design was decided by the committee of the lead session on 2026-11-15 (comments on #17, scope of #65)

Context: contract 11.3 asked a producer to stop posting once it saw RETIRING, as a duty of the process. A producer can post for up to a third of its heartbeat timeout after RETIRING, after the consumer's drain, and the record is accepted with `SCADA_OK` and then lost: an action without an audit record.
Options: leave it to the processes; let the library refuse posts in a RETIRING generation, with an ordering that makes every accepted post visible to the final drain.
Decision: the library refuses (contract 9.5).
- `scada_queue_post` returns `SCADA_E_RETIRING` on EVENTS and CMD queues in a RETIRING generation; RESULT posts are accepted (the library's ABORTED and EXPIRED answers, a driver's answer to a request it already took).
- Handshake: EVENTS loads the state before and after publishing; the `write_seq` store, both state loads, the RETIRING store of `scada-tagd` and the consumer's state and `write_seq` loads in `scada_queue_next` are seq_cst, with no fences. An event post that returned `SCADA_OK` is then always drained; one refused after publishing may still be delivered (a journal record of an action not taken, the safe side). CMD checks before publishing only, so that a requester is never told "refused" for a request a driver may execute.
- `scada_queue_next` in a RETIRING generation never waits: EVENTS and RESULT return what is left and then `SCADA_E_RETIRING`; CMD answers every request still queued ABORTED and returns `SCADA_E_RETIRING`. Detach in a RETIRING generation does the same for every request queue the process consumes. `scada_queue_post` stays real-time safe: two more loads of the state and the out-of-line calls of the handshake (about three plain calls, a few ns); no lock, system call or allocation.
Reason: a post that the library accepts after the consumer's last look is exactly the loss the "no audit, no action" rule forbids. The seq_cst order is the cheapest that closes it without a lock in the real-time post.
Consequences:
- Tests: `Queues.InARetiringGenerationOnlyAnswersArePosted`, `AConsumerDrainsARetiringQueueWithoutWaiting`, `RequestsLeftInARetiringGenerationAreAnsweredAborted`, `ADetachInARetiringGenerationAnswersItsRequestsAborted`, and the stress `EveryPostThatReturnedOkIsDrainedAfterRetire` (200 rounds of a poster against a consumer that retires and drains; it fails in every run when the second state load is removed).
- Contract 0.19: section 9.5 (new), 9.3 (the limit of a generation change), 11.3 step 2. The layout version stays 1.
- A drain looks at once for a producer region it has not mapped (`look_now`) before it can end. Found by the conformance test below: a consumer that attached before its producer, and whose generation retired within the second before its next look, drained nothing and lost every event a post had accepted.
- The library keeps no table of pending requests and no memory of ids, so those duties are the processes' (contract 9.5): a requester clears its pending table at detach and reports a request taken and not answered as failed with outcome unknown, never as ABORTED; a consumer keys remembered ids by generation; a driver never answers in the new generation a request taken in the old one.
- `scada-tagd` counts, when it removes or abandons a retired generation, the records still in each queue (`write_seq` minus the consumer's cursor) and logs one WARNING per queue: `audit records left unconsumed in a removed generation` for an events queue, `records left unconsumed in a removed generation` for a request or result queue. `RECORDS` is `unknown` when the queue file or the cursor cannot be read, the pair is not valid, or the generation was abandoned; a generation whose header cannot be read gives one record with `QUEUE` and `RECORDS` `unknown` (`Keeper.AGenerationWithoutAReadableHeaderIsReportedUnknown`, `ReportLog.AGenerationWithoutAHeaderGivesOneUnknownRecord`). Events a consumer never drained show there, so they are not counted again at detach.
- Committee review of PR #82 (C++, SCADA architecture, Linux; merge with conditions):
  - B1: the handshake is in the model check (tests/model): `handshake.litmus` for herd7, a post against the RETIRING store and a drain, with the loss as its forbidden condition, and six copies with one access made plain (three needed on Armv8, three not). In C++20 the cycle that forbids the loss is the post's `write_seq` store and second load and the drain's state and `write_seq` loads; the post's first load and the RETIRING store are outside it and are kept seq_cst out of caution, not because they are needed; its accesses moved into four functions of their own (`HeaderView::retiring`, `HeaderView::set_retiring`, `publish_write_seq`, `queue_write_seq_sc`) that `code_shape.py` checks in the ARM64 library, with six mutants. On Armv8.0 the code tells relaxed from seq_cst, not acquire from seq_cst; the call sites are checked by review and the tests. Known limit: for a queue file created anew during the retirement the litmus test covers `write_seq` only; that the drain which maps the new file after its state load sees its name and the release store of the header's `ready` field is not ordered by C++ there (on Armv8 the hardware forbids the bad outcome, and system calls are in between), and neither part checks it.
  - B2: detach looks for a producer region it has not mapped before its drain too (`Queues.ADetachAnswersRequestsOfAQueueItHadNotSeen`, which fails without it).
  - B3: on `SCADA_E_RETIRING` an event refused means the action is not taken; a request refused fails visibly as not executed; an OPERATOR command is never posted again by the service (reference 14.4: interlocks judged on the old state, a `select_request_id` of the old generation); AUTO writes are computed again by the next cycle, outputs hold or go safe until then (reference 5.5); selections do not survive a generation change.
  - B4: a driver executes and answers a request it took before it detaches, or drops it; it never acts on it after detach.
  - B5: the record of unconsumed records has MESSAGE_ID `42c8e35948cb467eb6d894d3bb0476a8`, the positions `[FIRST_SEQ, END_SEQ)`, "audit records" for an events queue, and RECORDS "unknown" when the pair cannot be read or is not valid, or the generation was abandoned; after the 30-s timeout the count is an upper bound. It is logged from `report_log.cpp` (`log_unconsumed`, tested field by field).
  - N1, N2: the C header says what SCADA_E_RETIRING of `scada_queue_next` means for RESULT, and that a drain makes system calls even with timeout 0. The look is not throttled: a consumer that gets SCADA_E_RETIRING stops calling, so it happens about once per drain.
  - N3: the stress test's consumer gives up after 10 s; the helper's pauses are pacing, said so, and its idle waits for SIGTERM with a limit.
  - N4: contract 15, test 21 reworded with its queue part; 11.3 cites reference 5.5; 9.5 states the two consequences of the handshake.
  - N5: issues #83 (command service, phase 5) and #84 (driver-interface contract, phase 2); #74 and #75 noted to cover the new record.
  - After #77 (D-49): `post_record` keeps the order first state load, refusals (the all-ones guard among them), high-water mark, record, seq_cst store of `write_seq`, second load. A drain looks at the producer's region by name also when one is mapped, and `drain_queue` drains the file in use and then a file created anew under the name, which `follow_queue` moves to (`Queues.ADrainFollowsAQueueFileCreatedAnewBeforeTheRetirement`, which fails with the old look: 0 of 2 events delivered). `poll` takes the retiring flag and calls `follow_queue`.

## D-56: Tests that failed under extreme overload: each cause, and the load the suite is expected to pass under

Status: proposed

Round 0 has no file of an earlier round, and on a loaded machine scada-tagd had not written the first one yet: "no valid retain file, round 0" (5 of 39 runs at load average 14).
